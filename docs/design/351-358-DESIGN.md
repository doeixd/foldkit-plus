# A window-scrolled list and a responsive picker (#351, #358)

Status: designed (2026-10-30); built in `foldkit-primitives` (`WindowViewport`,
`MeasureRow`) and `foldkit-mixins-ui` (`WindowList`, `Picker`,
`Recipes.Picker`), used in `examples/widgets`.

Both came out of planning the foldkit-domains port
(`foldkit-domains-PLAN.md`, gaps 1 and 9). The upstream app scrolls its 556
results with the document, and shows its filters as dropdowns on a desktop
and as bottom sheets on a phone, with the same options and state.

## 1. `WindowList`: a virtual list that scrolls with the window (#351)

### The problem

`@foldkit/ui`'s VirtualList and the `Virtual` primitive window a list inside
a scroller of its own: they read `scrollTop` and `clientHeight` of that
element. A list that scrolls with the page has to be given a fixed-height
box, which changes how the page scrolls and breaks three things the
document scroller gives for free:

- **Scroll restoration.** The browser restores the document's offset on back,
  forward and reload; it knows nothing of an inner scroller.
- **Sticky headers.** A `position: sticky` header sticks to the scroller it
  is in. In the page, it sticks while the results scroll; beside a nested
  scroller it stands still and takes room.
- **The page's keys and gestures.** Space, Page Down, End, a phone's
  collapsing toolbar and the scroll to top on a status-bar tap all move the
  document, not the box.

`Virtual`'s README said to "map the scroll entry into `Scrolled`". That is
wrong for any list with content above it: the window's `scrollY` is not the
list's own scroll position. What the windowing needs is where the viewport
lies over the list, which depends on the list's offset in the document, and
that offset changes when content above it changes size, with no scroll.

### Decision

```text
viewport over the list = { top: -list.getBoundingClientRect().top, height: innerHeight }
WindowViewport (Mount on the list) -> Placed -> update -> Model.viewport
view: visibleRange(keys, heights, viewport.top, viewport.height, overscan)
      -> start spacer, rows [start, end), end spacer, all in the document's flow
MeasureRow (Mount on each row) -> Measured -> Model.heights
```

1. **Where it lives.** The measuring is a primitive, the component is
   mixins-ui's.
   - `foldkit-primitives/state` gains `WindowViewport`, a Mount on the list's
     own box that reports `ViewportPlaced { top, height }`: how far the
     viewport's top is past the box's top (negative while the box is still
     below it) and the viewport's height. It reports on mount, on the
     window's `scroll` and `resize`, and when the box or the document's root
     element resizes, which is what content above changing size looks like.
     Equal readings in a row are sent once. The `Virtual` bundle needs no
     change: an application maps `ViewportPlaced` into `Scrolled({ top })`
     and passes `height` as `windowFor`'s viewport height; the README says so
     in place of the wrong sentence.
   - `foldkit-mixins-ui` gains `WindowList`, the component an application
     draws: a Model, two Messages and a view, on `Virtual`'s pure layout
     (`visibleRange`, `offsetFor`, `totalHeight`). It does not wrap
     `@foldkit/ui`'s VirtualList, whose Model holds a container's
     measurement and whose view draws its own scrolling `ul` with a Mount of
     its own (no window mode can be added from outside), and it does not
     place the `Virtual` bundle, whose scroll-settle timer and layout args a
     window list does not need.
2. **The rows stay in the document's flow.** The view draws a start spacer,
   the rows in range and an end spacer, so the list's box is as tall as every
   row (measured or estimated) from the first frame. Nothing scrolls but the
   document: restoration finds a page of the right height, a sticky header
   above the list sticks, and the page's own keys work. The browser's scroll
   anchoring (`overflow-anchor`, Chrome and Firefox) holds the rows in view
   still when a row above them is measured at another height than its
   estimate; nothing in the list turns it off.
3. **Heights are measured, border box.** Each row carries `MeasureRow`. It
   reported `contentRect.height`, the content box, so a row padded by a
   recipe was measured short and the rows below drifted. It now reports the
   border box (`borderBoxSize`), which is a fix for `Virtual` too. A row is
   drawn `display: flow-root`, so a child's margin cannot collapse through
   it and escape the measure; space between rows is padding, not margin.
   Unmeasured rows take `estimatedHeight`.
4. **Before the Mount reports** (a server render, the first frame), the
   Model assumes the viewport at the list's start and `viewportHeight` tall
   (default 1000), so the first rows and the full height are drawn.
5. **Model.** `{ id, estimatedHeight, overscan, heights, viewport: { top,
   height } }`. Messages `Placed { top, height }` and `Measured { key, height
   }`; each returns the Model it was given when nothing changed. `keep(model,
   keys)` drops the heights of rows that left, as `Virtual`'s `Prune`, and
   `windowOf(model, keys)` answers which rows are drawn, for an application
   that loads what is in view (the domains port's quote reads).
6. **Slots.** `root` (the list, `role="list"`), `spacer` (both ends,
   `data-edge="start" | "end"`, hidden from assistive technology), `row`
   (`role="listitem"`, `aria-posinset`, `aria-setsize`). The spacers' block
   size and the rows' `display` are inline: a theme may not change them, the
   windowing depends on them. No recipe: the list has no look of its own.
7. **Keys.** The offsets table is cached by the keys array's identity. The
   view derives the keys from `items` and `itemToKey`, cached by the identity
   of both, so a view that keeps its items array pays O(n) once per change
   of items or heights, not once per scroll.

### What it does not do

- **Restore row-exact after a reload.** Heights are measured again from
  scratch, so a restored offset lands on the same pixel, not necessarily the
  same row, where rows differ from the estimate. An application that must
  can keep `heights` and give them back.
- **Programmatic scrolling.** The document scrolls itself: `window.scrollTo`
  and an element's `scrollIntoView` (which honours `scroll-padding-top` under
  a sticky header) are the application's, and End is the browser's key.
- **Safari's anchoring.** Safari has no `overflow-anchor`, so there a row
  above the viewport measured taller than its estimate moves what is in view
  by the difference, once.
- **Horizontal or grid windowing.** One axis, as `Virtual`.

### Rejected

- **A window mode on mixins-ui's `VirtualList`.** Its Model is upstream's,
  measured by upstream's Mount on upstream's `ul`. A `scroll: 'window'` flag
  there would mean forking `@foldkit/ui`'s virtual list.
- **Absolutely positioned rows** (TanStack Virtual's window mode). In-flow
  rows keep the browser's scroll anchoring, let a row's content be `sticky`
  against the viewport and need no measured container width.
- **Reading `window.scrollY` minus an offset measured once.** The offset
  moves when a banner above opens; the reading must be relative to the box
  every time.

### Tests

- Unit (Model): `Placed` and `Measured` keep the Model on equal readings
  (`toBe`), a poisoned height is ignored, `keep` drops departed keys and
  returns the Model when none left, `windowOf` covers the viewport plus
  overscan and draws nothing past the end.
- `WindowViewport` in jsdom: reports on mount, on window scroll, dedupes
  equal readings, and detaches on teardown.
- Browser, at 1280×800 and 390×844, with a sticky header and a block above
  the list and a footer below it: the document is the list's full height
  before any scroll; scrolled anywhere, the drawn rows cover the viewport and
  number fewer than forty of a thousand; the list's box never scrolls
  (`overflow` visible); the header stays at the viewport's top; the footer
  starts where the last row ends; content above growing moves the rows drawn
  without a scroll; after every row was measured, each row starts at the sum
  of the measured heights above it.

## 2. `Picker`: a dropdown on desktop and a sheet on a phone (#358)

### The problem

foldkit-domains shows its availability filter and sort as Listboxes on a
desktop and in Sheets on a phone. The upstream app keeps two Models and two
code paths and hides one with a media query; an application on Foldkit Plus
would do the same: a Listbox Model, a Sheet Model, a list of options drawn
twice, and an `update` that writes the same choice from two Messages.
`Sidebar` already shows one way out (its `sheet` option draws an opener and a
Sheet below `md`); a select had none.

### Decision

```text
desktop (at or above the breakpoint):  Listbox trigger -> Listbox panel -> Selected
phone   (below it):                    opener -> Sheet -> option pressed
                     both -> OutMessage Chose { value } -> the application's update
```

1. **The application owns the value**, as with `@foldkit/ui`'s Listbox: the
   view takes `value: Option<Value>` and `update` returns `Chose({ value })`
   as an OutMessage. The Picker's Model holds only interaction state:
   `{ id, listbox, sheet }`, upstream's Listbox Model and this package's
   Sheet's. The Model, the Messages and the OutMessage are one type whatever
   the width: nothing in `update` reads the viewport, and a choice made
   either way reaches the application as the same `Chose`.
2. **Both presentations are drawn; CSS shows one.** The view draws a
   `dropdown` box holding the Listbox (its trigger and its panel, anchored
   with `portal: false` so the panel stays in the box) and an `opener`
   button beside it, which opens the Sheet. `Recipes.Picker` hides the
   dropdown below the breakpoint and the opener at or above it. A hidden
   element is `display: none`, out of the accessibility tree and the tab
   order, so a reader meets one control. No Mount reads the width, so the
   Picker sends no Message a Scene test must resolve, and a server render is
   right at every width.
3. **The breakpoint is a theme token.** `Recipes.Picker({ sheetBelow })`
   takes a name of `Theme.tokens.breakpoint` (`sm`, `md` (default), `lg`)
   and hides each half with `@media not all and <that query>`, as `Sidebar`
   and `AppShell` do. An application whose theme overrides the breakpoint
   gets the same switch in CSS.
4. **Crossing the breakpoint while open.** Opening the Sheet closes the
   Listbox, so a Listbox left open behind a narrowed window does not open
   alongside. A Sheet open when the window widens stays open and usable over
   the desktop layout until it is chosen from or dismissed: closing it on
   resize would need a Mount reading the width, which point 2 rules out.
5. **The sheet's list is a listbox.** `list` is `role="listbox"`, labelled by
   the Sheet's title; each `option` a `button` with `role="option"` and
   `aria-selected`. The chosen option (or the first) takes the Dialog's
   initial focus and is the only one in the tab order; ArrowDown, ArrowUp,
   Home and End move focus between options (a `Command`, no Model change),
   Enter, Space or a tap chooses, which closes the Sheet and returns focus to
   the opener (the Dialog's). An option's content is `Listbox.parts`'
   `option`, so its icon, label, description and check are the Listbox's
   slots and look, and the check shows on the chosen row by the same
   `aria-selected` rule.
6. **Every element is a Slot.** `PickerSlots`: `root`, `dropdown`, `opener`,
   `list`, `option`. The Listbox's elements are `ListboxSlots` (styled by
   `listbox`'s mixins, `Recipes.Listbox`), the Sheet's `DialogSlots`
   (`sheet`'s mixins, `Recipes.Sheet`), and the trigger's and opener's
   content (value, placeholder, chevron) `Listbox.parts`' `trigger`. The
   opener takes the Listbox trigger's look from shared recipe pieces, so the
   two read as one control.
7. **API.** `Picker.init({ id, sheet? })`, `Picker.update(model, message)`
   (a `ReturnWithOutMessage`), `Picker.view({ model, onMessage, label,
   options, value, placeholder, anchor?, style?, listbox?, sheet? }, h)`.
   `options` are `{ value, label, description?, icon? }` with `value` typed
   `Value extends string`.

### Rejected

- **One trigger that opens whichever fits.** `update` would have to know the
  width, so the Model would hold it (it would change with the presentation)
  or a Mount would send it.
- **One panel styled as a popover or as a sheet by CSS.** A desktop dropdown
  is non-modal and anchored; a phone sheet is a modal dialog with a focus
  trap, scroll lock and a drag. The two Models already own those; restyling
  one as the other loses half.
- **Radio buttons in the sheet.** A radio group checks on every arrow key,
  and a choice closes the sheet, so arrowing would close it at the first
  step.

### Tests

- Unit: `OpenedSheet` opens the Sheet and closes the Listbox; a Listbox
  selection and a sheet option both return `Chose` with the value and close
  what was open; a step between options returns the same Model (`toBe`) and
  one focus Command; every other no-op returns the Model given.
- Browser at 1280×800: the opener has no box, the trigger has one; the panel
  opens under the trigger; a choice updates the trigger's text and focus
  returns to it. At 390×844: the trigger has no box, the opener has one;
  the Sheet's panel spans the width and stands on the bottom edge; focus
  starts on the chosen option, arrows move it, Enter chooses, the Sheet
  closes and focus returns to the opener. `sheetBelow: 'lg'` at 800px shows
  the opener.
- Touch (`*.touch.browser.test.ts`, 390×844): a tap on the opener and a tap
  on an option choose; a swipe down dismisses without choosing.
- Types: `Value` flows from `options` to `value`; a `value` outside the
  options' type is refused; `onMessage` does not infer from its result.
