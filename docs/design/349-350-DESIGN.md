# A prediction holds still, and disagreeing fails the test (#349, #350)

Status: built (2026-10-30).

## The problem

Chirp drew a posted chirp, then moved it 27px when the server answered: a
status line said "1 chirp waiting to send" above it while the write was on
its way (`fdf7e79d`). Every test passed. Two checks were missing, one per
side of the wire:

- `Behaviors.optimistic` asserted that the predicted element showed before
  the answer and showed after it. What happened in between (removed, drawn
  again, pushed down, hidden) was nobody's assertion.
- `Remote.make({ verifyPredictions })` compares each prediction with the
  server's answer, and `Data.timeline` flags a read that stopped showing its
  value. Both only report, at warning level, and only where an application
  opted in. No test fails on either.

## Decision

```text
#349  shows appears ──── watched: same node, same parent, same place, visible ──── settled
                                                                                    = no Remote request in flight
                                                                                      (or the page's own evidence), then quiet frames
#350  answer lands ── PredictionMismatch (error) ──┐
      Model changes ── timeline regression ────────┴─> Trace.run / Trace.record throw
                                                      unless the domain declares it expected
```

### 1. `Behaviors.optimistic` watches what it predicted (#349)

From the moment `shows` is visible until the write settles, every element it
resolves to must:

| Stays | Seen by | Fails as |
| --- | --- | --- |
| in the document | `childList` records naming it or an ancestor, replayed in order | removed |
| the same node | the locator, once settled, resolving to another element | replaced |
| where it was in its parent | a removal record of it (or an ancestor) after which it is attached again | moved within its parent |
| where it was on the page | its box in document coordinates, every frame; more than 1px off its first | shifted by layout |
| visible | `hidden` records replayed with `attributeOldValue`; `checkVisibility()` every frame | hidden |

Records are replayed, not read in the callback, because a callback sees the
element as it is now: a node removed and put back in one batch reads as
attached (AGENTS.md, "A MutationObserver callback sees the element as it is
now"). Layout and visibility are sampled per frame because that is what a
reader sees; a hide undone within one task never paints, and a style that
moves a box writes no record of the element.

**Settled is evidence, not a sleep.** Over HTTP, every Remote request the
page makes from `act` on is counted (mutations held for `hold` as before,
and the queries an answer leads to, such as `verifyPredictions`' first page
of a placed list); settled is when none is in flight, followed by quiet
frames (three in a row with no change to the document), checked again. A
write that travels another way (Chirp's port to a SharedWorker) takes
`writes: { answered }`: the page holds its own answers, and `answered`
resolves on the page's own evidence that nothing is pending.

**Narrowing and opting out.** `stays: 'put'` (the default) watches `shows`;
a `Locator` watches what it resolves to instead (the title inside a row
whose controls the answer redraws); `stays: 'shown'` keeps only the old
check, for a write whose view deliberately draws again. Each is visible at
the call.

**Errors fail it.** An error the page logs between `act` and settled fails
the write, with the line: under `verifyPredictions` a `PredictionMismatch`
is logged at error level (§2), so an end-to-end write is checked against its
answer by the call already in every example.

### 2. `PredictionMismatch` is an error, and verification is declared (#350)

- `PredictionMismatch` is reported at `level: 'error'`. A disagreement is a
  defect of the prediction or of the server, not advice. The default
  reporter writes errors to `console.error` (#272), which `consoleErrors`
  and §1 read.
- **How the mode is known.** No package reads a build mode, and a domain is
  declared once, in a module that the page, the tests and the server import.
  The application says it where it declares the domain:
  `verifyPredictions: import.meta.env?.DEV === true`. Vite's dev server and
  Vitest define `DEV` as true; a production build defines it false; `tsx`
  has no `import.meta.env`, hence `?.`. Every example declares it so.
  Verification costs a fetch of each placed list's first page per write,
  which is why the package's own default stays off.
- **Tests require it.** `Trace.run` refuses a domain that registers a
  mutation and does not verify (`Data.verifiesPredictions` is false): a
  trace over one cannot see a disagreement, and passing would read as
  agreement. A domain that writes nothing predicts nothing an answer
  settles, and runs either way (#368).
- **A deliberate disagreement is declared, typed, with a reason.** The
  object form names the parts the server is meant to answer otherwise:

  ```ts
  verifyPredictions: {
    on: import.meta.env?.DEV === true,
    expected: {
      mutations: { postChirp: { Value: 'the server stamps the time it stored the chirp' } },
      queries: { timeline: { Placement: 'the server ranks by engagement' } },
    },
  }
  ```

  Names are checked against the domain's own mutations and queries (an
  unknown name is a type error), a reason may not be empty (refused where
  the domain is made), and an expected part records nothing. The silencing
  is in the declaration, where a review sees it, and holds in development
  as in tests.

### 3. The testing hooks fail on a disagreement (#350)

`foldkit-remote/testing` reads disagreements from the Models themselves:
each recorded Model's `diagnostics` holds every `PredictionMismatch` the
reducer recorded (it is pure, and records before anything reports).

- **`Trace.run`** throws once its steps have run when any Model of the trace
  recorded a `PredictionMismatch`, or when a read in `config.reads` regressed
  (`Data.timeline`'s rule) and `config.regresses` does not name it with a
  reason. The error names the step, the Message's tag, and the mismatch's
  words or the read's `Data.why` message.
- **`Trace.record(Data, update, options)`**, for a runtime in a browser
  test: wraps `update`, keeps every Message and the Model after it, and
  `check()` throws as `Trace.run` does. A test calls it once its steps are
  done. It refuses a domain that does not verify, as `Trace.run` does.

Timeline regressions are checked only for reads a test names: which reads
matter is the test's to say, and the rule is the one `Trace.regressions`
already applies. The Model alone cannot say which projections the view reads.

## Ownership

Nothing here owns state. `Behaviors.optimistic` observes the page;
`Trace.run` and `Trace.record` read Models the application's own `update`
produced; `verifyPredictions` compares inside the reducer as before and only
changes what it records.

## Not done

- **Timeline regressions end to end.** A Playwright page has no Model to
  fold; §1 sees what a regression draws (a row replaced, a list emptied).
- **Expected disagreements per field.** A mutation's parts are named
  whole (`Value`, `Gap`): a descriptor does not carry its Entity's fields
  in its type, so a field list could not be checked.
