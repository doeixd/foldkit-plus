# Performance: server CPU, client size, layout shift

Status: plan (2026-11-02). Issues #413–#440, under #411. The principle
behind the "Beyond parity" levers is
[declared-optimization-DESIGN.md](./declared-optimization-DESIGN.md): Plus
knows what each region reads and sends, what each page needs and who may
see it, and every optimization that trusts a declaration ships a
development-mode checker that catches a declaration that lies.

## Why

domains-plus is the same app as Foldkit's own `foldkit-domains` and the
Solid 2.0 recreation in `doeixd/solid-domains`, so the three compare
directly. Measured 2026-11-02 with solid-domains' `scripts/benchmark.mjs`
(15 cold loads per site, medians), PageSpeed Insights, and its line counter:

| | Solid 2.0 | stock Foldkit | Foldkit Plus |
| --- | ---: | ---: | ---: |
| Loads failing with 1102 | 0 of 15 | 0 of 15 | 107 of 117 |
| Time to first byte, ms | 64 | 52 | 1,292 |
| Top Results priced, ms | 188 | 619 | 1,404 |
| New search, ms | 213 | 251 | 269 |
| JavaScript, brotli | 79 KB | 215 KB | 289 KB |
| HTML, brotli | 5.4 KB | 4.5 KB | 27.7 KB |
| CLS, desktop | 0 | 0.771 | 0.787 |
| App code, lines | 2,664 | 3,280 | 2,928 |
| Style code, lines | 933 (CSS) | 710 (CSS) | 1,126 (`style.ts`) |

The Foldkit Plus timings come from its 10 loads that answered. Its pages are
whole without JavaScript (the server reads every price it shows), which is
the right design and the reason its server work matters: every page costs
CPU before its first byte.

## Where it goes

**Server CPU** (`Cpu.budget`, #339; a V8 profile of `/?q=acme`):

| Cost | Share | Issue |
| --- | --- | --- |
| Foldkit's server re-parses its own output with parse5, about 16 times a page in 0.170 | ~175 ms | #413, upstream foldkit/foldkit#1657 |
| Garbage collection, mostly from the above | ~55 ms | #413 |
| Drawing the view: 66 priced names | ~38 ms | #415 |
| `Style.usedIn` scanning the rendered HTML | unmeasured | #414 |
| Cold start: a 2.1 MB Worker bundle evaluated per isolate | 345 ms cold against 135 ms warm under Node | #416 |

Re-measured 2026-11-09, with #415, #419, #434 and #436 landed: a never-seen
search (`/?q=<word><n>`, so no kept page serves it) is a 69 KB page and about
119 ms warm CPU under Node on Linux (median of 20). The profile splits it as
parse5 41 ms, the rest of Foldkit 25 ms, garbage collection 11 ms, Effect 7 ms,
and the packages and the app about 12 ms together. All of parse5's time is
Foldkit checking its own output (`escapesDocumentStructure` 14 ms,
`parseFragmentModes` 13, `closesCleanly` 8, `assertInjectionIsFaithful` 5,
`renderedShapes` 5), so what is left of #413 is upstream's (#1657).

On workerd (2026-11-10, Linux, workerd 1.20261019, commit dce71b1): the same
kind of page, built by `vite build` and run as it ships, costs a median of
125, 137 and 150 ms warm in three runs of 20 requests (worst 160 to 198 ms;
the first request of each run, a cold isolate, 267 to 318 ms). Each request
asks a word never asked before, so no kept page serves it. That is about
15 ms above the Node figure, and far from #413's goal of under 30 ms: the
checks left are upstream's. Read with `node scripts/workerd-cpu.mjs`, which
runs the built `dist/server/fetch.js` with the app's own `wrangler.jsonc` on
the Wrangler the app pins, straight to the Worker (not over HTTP), by the
main thread's `schedstat` as `stack.cpu` reads it. `Stack.start` could not
take it: it bundles a source entry, and this Worker is generated by
`@foldkit/vite-plugin`. The page was 90 KB here against 69 KB under Node,
so the two figures are not of the same bytes.

Why (2026-11-10, `/?q=acme`, 89,222 bytes on workerd against 69,406 under
Node through the same `handleRequest`, tag by tag): the built page carries a
`data-foldkit-identity="<16 hex>"` attribute on 487 elements, 19,967 bytes,
which is the whole gap. They are Foldkit's hydration markers: the
`foldkit:view-identity` transform in `@foldkit/vite-plugin` brands every view
function, and a hydratable render stamps its identity on each element it draws
so hydration can check it adopts the same logical entity (`foldkit/dist/
hydrationMarkers.js`; the client reads and strips them). Vitest and `tsx` load
no plugin, so the Node page has 3. With the attributes taken out the two pages
are 69,250 and 69,283 bytes; the head differs (the font preload's path, the
linked sheet) and nothing else does. Nothing else is inlined (the sheet is linked in both, the resume data is
10,714 bytes in both), and the markers are cheap on the wire (brotli 6,051 against
5,539 bytes) but are 29% more HTML for parse5 to read, which the Node CPU
figure above does not include. It is not a defect of domains-plus's build:
the markers are on whenever the plugin brands a hydratable view, and no
option of the plugin or of `foldkit-ssr` turns them off. A Node figure of the
page as shipped needs the branding transform in the measuring run, and CPU
read under Node is of the smaller page until then. Upstream could stamp one
marker per view function's root rather than per element (38 distinct values on
487 elements); that is not asked yet.

The parse cost is Foldkit's, and upstream is reducing it.
foldkit/foldkit#1657 (P2) tracks it with a reproduction: about 80 ms on a
52 KB page. Its first step, #1659, cut parses from 26 to 16 and is in
0.170. Its next step, not validating again in `injectIntoTemplate` the
exact HTML `renderToString` already validated, is open, and the maintainer
would raise it to P1 if the cost blocks a deployment, as ours does. The
cost grows linearly with what is parsed, and our page is about 362 KB
uncompressed against the reproduction's 52 KB. Most of the difference is
ours to remove:
- the inline stylesheet, about 92 KB (#419);
- a second `usedIn` `<style>` block (#414);
- every priced row (#415);
- the resume data (#436).

A serializer of our own was considered and rejected: it would have to track
Foldkit's hydration markers and build stamping exactly, to work around a
cost upstream is already cutting for every Foldkit SSR app. Effect Schema
and seroval serialize data, not HTML. The resume data already goes through
Effect Schema, and JSON encoding does not show in the profile.

## How Foldkit Plus can beat base Foldkit

Base Foldkit gives a program contract and a runtime: one Model, `update`, a
virtual DOM drawn whole on every Message, and a server that renders a shell.
Plus knows more about each program than the runtime does: what each region
reads (Surfaces, Projections), what data a page needs and how fresh it may be
(Remote, Entity, Query bodies), which Messages a region can send, and what is
fixed at build (styles, routes). Every lever below spends that knowledge.

| Lever | What Plus knows | Issues |
| --- | --- | --- |
| Data in the first paint, read once | A page's reads, resumed instead of refetched | built (#388); cheap with #413–#416; started at route match (#435) |
| Render once what never changes | Which regions read nothing per request | #434 partial prerendering |
| Send only what the client reads | Which Model slices interactive regions read | #436 |
| Check only what a Message can change | Each region's reads against each Message's writes | #439 invalidation map |
| Catch a slow Query at build | Every filter and order is declared | #437 index checks |
| Split per route | The Site tree's Bundles and Surfaces | #438 |
| Decode only what a page reads | Each page's Selections | #440 |
| Fewer requests | A normalized store, derived refresh | built (#386 single flight, #401 Back and Forward); #428 caches public reads and pages at the edge |
| Less work per update | What each region reads | #431 memoizes regions by it by default (built opt-in: #384, #385) |
| Less work at build time | Styles and their classes are fixed per build | #419, #420 |
| Less JavaScript for display | Which regions send no Messages | #432 islands |
| Platform over script | Recipes own the components | #429 `content-visibility` lists, #430 popover, anchor positioning and `<dialog>` |
| Earlier first byte | Which regions are first-screen | #427 streams the first screen first |
| A different renderer | Surfaces declare reads; `react-codegen` compiles views | #433 compiled views, with #376 |

Stock Foldkit's domains app reaches priced Top Results in 619 ms because it
fetches after its script runs; Solid reaches them in 188 ms by pricing on the
server. domains-plus already prices on the server, so once rendering is
cheap it should match Solid there, a 3× gain over base Foldkit that a runtime
alone cannot reach.

## The floor

Foldkit's virtual DOM plus Effect's runtime is a floor on client bytes that
nothing short of #432 or #433 lowers: 91 KB brotli for Foldkit and Effect in
domains-plus, measured by #421. Solid's 79 KB is below it. Plus also adds code base
Foldkit does not have (Remote, Entity, Site); it is a net gain only where it
replaces application code and requests, as it does in domains-plus (2,928
lines against 3,280, prices in the first paint). #378, #396 and #397 keep a
read-only page free of what it does not use; #421 extends that discipline to
whole applications with a budget.

A new search, re-measured 2026-11-09 against stock Foldkit's copy in
`examples/foldkit/domains`, both built and served by `wrangler dev --local`
(`scripts/search-compare.mjs`, medians of 20 and 12 interleaved searches,

the CPU slowed four times. Which change since 0.38.0 moved it ahead is not
split out beyond #474's own `answeredOf` cut; the live Workers have not been

Server CPU is the one number that decides the rest. Solid spends 5–12 ms on
this page; domains-plus about 60 ms on `/` and 190 ms on a search, against
the free plan's 10 ms. About 85% is Foldkit's checks of the server markup
(#413), but without them a search is still about 28 ms, so even upstream's
fix leaves never-seen searches over the limit. Caching and prerendering
cover repeated pages only; the render itself must cost less (#473).

In 0.38.0 a URL left idle for minutes failed 15 of 15 times. A probe
disproved the first guess: the Cache API does keep responses on
`workers.dev` (3 of 3 hits after 5.5 idle minutes). domains-plus kept a page
for its 60 s freshness only, so an idle URL had expired and rendered again.
#468's `CacheStore.kv` with `keep: '6 hours'` fixed it: after six idle
minutes, 10 of 10 loads were served from KV, and Worker startup fell from
539 to 327 ms.

## What the work so far taught

- **Measure the check before skipping it.** #439 would skip checking the
  regions a Message cannot affect. Measured 2026-11-09 (`pnpm bench`,
  `packages/remote/bench/read.bench.ts`):
  - a region over Model paths checks a few identities, well under 1 µs;
  - a Remote read with the store unchanged is a memo hit, 1.3 µs;
  - one read again after a write to a row it does not show costs about
    22 µs for a 25-row list and 100 µs for 100 rows.

  A page with five 25-row lists spends about 0.1 ms per write re-checking,
  about 1% of domains-plus's 9 ms view frame. That is the most #439 could
  save, so it waits for a page with many long lists (ten 100-row lists is
  about 1 ms). Its static half, which queries a write can reach, is already
  derivable (#477's `candidate`, `packages/remote/test/writeTrace.test.ts`).

- **A memo is measured where its case happens.** #431's Bundle part is
  built: a placement, a `Link.child` and a collection item drawn without
  view inputs are kept while the child's Model is the same object. No app the
  render benchmark drives has the case it helps: the data grid is one
  placement whose Model changes with nearly every Message, domains-plus
  places no Bundle children, the CMS studio draws one section at a time, and
  ui-showcase folds its components with `Update.foldChild` and draws them by
  hand. Its runtime test counts draws (`packages/bundle/test/memo.test.ts`);
  numbers wait for an app with sibling placements that stand still while
  others change.

- **Measure what a sheet holds before pruning it.** #471 proposed shipping
  only the classes a page can draw. Measured 2026-11-08 on domains-plus, its
  sheet is 159.6 KB raw, 15.2 KB brotli: 92.0 KB of it is the application's
  own `stylesheet` text (reset, theme, defaults), and 67.7 KB the compiled
  classes. Server renders of `/`, three searches, `/tlds`, a 404 and a page
  with a cart draw 114 of the 148 classes; the 34 left are about 12 KB raw,
  about 1.2 KB brotli, and nearly all are drawn later by a client (the
  Listbox and Dialog popups, the filter and cart sheets, data-dependent
  states), which would then inject them at run time. The lever is the base
  sheet: 414 of its 587 token definitions are read by nothing the sheet
  ships, and dropping them would take it from 15.2 to 10.8 KB brotli (#487).
  Built (`styles({ prune })`), a `vite build` measured 10.6 KB, held by
  `examples/foldkit/domains-plus/test/sheet.test.ts`.

- **Remove code; do not defer it.** #423 moved the cart and phone sheets
  behind `Resource.lazy` and saved 0.9 of 214.8 KB: the app's own code is
  small, and the weight is in libraries (Effect, Foldkit, `@foldkit/ui`,
  floating-ui, the style system). It was reverted. #430, #420 and #472
  remove or skip code instead.
- **A component's update and view in one module cannot be split.** The
  Model needs the update from the first frame, so `foldkit-mixins-ui/sheet`
  keeps its view in the first chunk too. New components should keep them in
  separate modules.
- **A view cannot wait on `Resource.lazy`.** Loading a view's code later
  needed a module-level cell outside the Model. If deferring views ever pays,
  that is a missing API (loaded code as Model state), not app code to write.
- **Measure before filing.** #423 and #464 were cut with estimated savings,
  and both measured a tenth of the estimate or less (#464's bytes come from
  `@yielded/auth-persistence-drizzle`, not from us). The JS budget had 4 KB
  of slack and 4 KB of growth passed unnoticed; a budget sits about 1% above
  what it measures.
- **The free plan's CPU limit binds every render, background ones too.**
  Re-rendering a kept page in `waitUntil` fails like the request would, so a
  kept page cannot refresh itself there. Freshness comes from the client
  re-reading data past its `maxAge`, which is cheap; the server renders a
  page once, at build (#469) or on its first request (#468).
- **A cheap server makes the no-JavaScript path safe to lean on.** #472
  starts the runtime on intent, so until then a search is the GET form, a
  full server render. That only helps once the render fits the limit (#473),
  and the runtime should start on hover or focus so the form stays a
  fallback.

## What we keep

Rendering prices on the server stays. It is why the page works without
JavaScript (#388) and why the first screen can be priced at first paint,
which neither client-priced Foldkit nor a slower server can match. The plan
makes that work cheap rather than removing it.

The fidelity Foldkit's checks protect stays too, moved to where it is
cheap. A page whose markup a parser would rebuild differently is still
refused, by the conformance suite and the per-build check, instead of on
every request.
