# `foldkit-ssr`

**Location:** `doeixd/foldkit-plus/packages/ssr`
**Package:** `foldkit-ssr`
**Status:** experimental / design proposal

> **Status: not started, and — unusually for this repository — nothing is
> stopping it.**
>
> There is no `packages/ssr`. That matters to record because most unbuilt work
> in these design documents is *gated*: Phase 13 waits on a query that wants a
> join, §21's containment waits on an application paying for it, the reactivity
> packages wait on primitives that have to land in `foldkit/foldkit` first. A
> reader who has learned that pattern will assume this is gated too.
>
> It is not. This is eight phases of ordinary unstarted work with a written
> plan, and the only thing between here and Phase 0 is someone doing it.
>
> Phase 0's premise checks out: Foldkit core already has the SSR behaviour to
> clone — `renderToString`, `toResponse`, flags encoding and hydration-root
> validation in `foldkit/experimental/server` (verified against `foldkit`
> 0.158.2). So the first phase is a port with a known target rather than a
> design question.
>
> **It deserves its own plan and its own run.** At 3,000 lines and eight phases
> it is the largest single piece of work left anywhere here, and it shares
> almost nothing with the query and interpreter work that surrounds it — §18 is
> a `foldkit-remote` integration and §14 is Surface-oriented, but neither
> reuses the machinery. Appending it to a pass whose purpose was to settle
> deferred items would misrepresent both: this is not a deferred item, it is an
> unstarted project.

## Goal

Start by reproducing Foldkit's existing SSR behavior behind a standalone `foldkit-ssr` package, then progressively improve it so that:

1. server rendering remains one-shot and deterministic;
2. request/server data does not have to be serialized again just because it produced HTML;
3. the browser does not rerun `init`;
4. server-only portions of the view are not rerendered during hydration;
5. only client-owned Model state crosses the server/client boundary;
6. `Surface` becomes the declaration of client observation requirements;
7. `Remote` can hydrate only the exact recoverable server facts interactive Surfaces need;
8. eventually, server-only render code itself can disappear from the client bundle;
9. a later phase can explore true binding-level resumability.

The conceptual shift is:

```text
current Foldkit SSR

Flags
  │
  ├─────────────── server
  │                  │
  │                 init
  │                  │
  │                Model
  │                  │
  │                 view
  │                  │
  │                 HTML
  │
  └─────────────── serialized Flags
                     │
                     ▼
                   browser
                     │
                    init
                     │
                   Model
                     │
                    view
                     │
                 DOM adoption
```

becoming:

```text
foldkit-ssr

                    server Model
                         │
             ┌───────────┴────────────┐
             │                        │
             ▼                        ▼
       complete server view      Resume Projection
             │                        │
             ▼                        ▼
           HTML                 small state payload
             │                        │
             └───────────┬────────────┘
                         ▼
                      browser
                         │
              baseline Model + payload
                         │
                         ▼
                  client Model
                         │
                client-owned view
                         │
             adopt existing server DOM
```

Foldkit already gives us the first server-side optimization: current SSR resolves `init`, runs the pure view once, and does not run `update`, Subscriptions, or Managed Resources on the server. The current client hydration path then reads serialized Flags, calls `init` again, executes the same view, and adopts matching DOM.

So `foldkit-ssr` should concentrate primarily on **the handoff and client startup**, not reinvent server rendering.

# 1. First principle

The main rule should be:

> **The Model used to render the complete server HTML is not automatically the state that must cross to the browser.**

More specifically:

```text
server render ownership
    ≠
client runtime ownership
```

A page may use:

```ts
type Model = {
  post: {
    id: string
    title: string
    body: string
    liked: boolean
  }
}
```

but the browser may only need:

```ts
{
  post: {
    id: string
    liked: boolean
  }
}
```

because:

```text
title ─┐
       ├──> server HTML only
body ──┘

id ────┐
       ├──> live client behavior
liked ─┘
```

That distinction should become explicit rather than being inferred from "whatever happened to be in Flags."

---

# 2. Why `Surface` is the right substrate

This package should **not invent another component or projection system**.

`foldkit-surface` already says exactly what we need:

> a Surface declares which part of the application's Model a consumer observes and which Messages it may cause.

Its `Projection`s already carry a codec, pure reader, dependency paths, metadata, and — for writable projections such as `Projection.pick` — `get` and `set`.

That gives SSR a very natural interpretation:

```text
Surface
   │
   ├── Model dependencies
   │        ↓
   │   data client code actually needs
   │
   └── Message subset
            ↓
       behavior client must activate
```

So the architecture should become:

```text
                 Foldkit Model
                       │
          ┌────────────┴────────────┐
          │                         │
    complete server view      active Surfaces
          │                         │
          ▼                         ▼
        HTML                client dependency closure
                                    │
                                    ▼
                              Resume state
```

This is a direct extension of what `Surface` already does for Remote, Sync, Agents, and other interpreters rather than a new state architecture.

# 4. Phase 0 — clone Foldkit SSR behavior exactly

Do **not** begin by copying `server.ts` line-for-line.

The current implementation reaches deeply into private Foldkit internals: hydration markers, Snabbdom VNodes, runtime singleton state, DOM reflection, serialization, boundary bookkeeping, etc.

Instead, clone its **public behavior and test contract**.

Initially:

```ts
// foldkit-ssr/server

import * as FoldkitServer from 'foldkit/experimental/server'

export const renderToString = FoldkitServer.renderToString
export const injectIntoTemplate = FoldkitServer.injectIntoTemplate
export const toResponse = FoldkitServer.toResponse
```

and similarly:

```ts
// foldkit-ssr/client

import * as Runtime from 'foldkit/runtime'

export const hydrate = Runtime.hydrate
```

Then port or recreate upstream SSR integration tests into `packages/ssr/test/parity.test.ts`.

The first milestone is:

```text
foldkit-ssr behavior
        ==
foldkit/experimental/server behavior
```

before adding anything.

This matters because Foldkit's existing SSR already contains a lot of hard-won correctness around HTML parser behavior, build IDs, keyed identity, controlled inputs, custom elements, `InnerHTML`, and hydration mismatches. The existing server implementation also stamps a deployment build ID specifically to prevent stale HTML from hydrating against incompatible client code.

### Phase 0 acceptance criterion

This:

```ts
import * as Server from 'foldkit-ssr/server'
```

should be a drop-in replacement for:

```ts
import * as Server from 'foldkit/experimental/server'
```

for existing SSR examples.

No optimization yet.

# 5. Phase 1 — introduce a versioned Resume Plan

Next add the first new Foldkit Plus primitive:

```ts
const Resume = SSR.plan(App, {
  id: 'main',
  state: ClientState,
})
```

where `ClientState` is a writable Projection.

For example:

```ts
const ClientState = Projection.compose(
  Projection.pick(
    App.fields.route,
    App.fields.viewer,
  ),
  Projection.pick(
    App.fields.post.id,
    App.fields.post.liked,
  ),
)

export const Resume = SSR.plan(App, {
  id: 'post-page',
  state: ClientState,
})
```

Conceptually:

```ts
interface ResumePlan<Model, State> {
  readonly id: string

  readonly state: {
    readonly schema: Schema.Codec<State>
    readonly get: (model: Model) => State
    readonly set: (model: Model, state: State) => Model
    readonly dependencies: DependencySet
  }

  readonly baseline: () => Model
}
```

For a `RunnableApplication`, `baseline` defaults to:

```ts
() => App.initial
```

Otherwise the user supplies it explicitly.

### Why a baseline Model?

Because we don't actually want a partial invalid Foldkit Model.

Client startup becomes:

```text
App.initial
    │
    ▼
valid complete baseline Model
    │
    + resumed client state
    │
    ▼
valid complete client Model
```

So if:

```ts
App.initial = {
  route: Home,
  post: {
    id: '',
    title: '',
    body: '',
    liked: false,
  },
}
```

and the resume state contains:

```ts
{
  route: Post('123'),
  id: '123',
  liked: true,
}
```

we reconstruct a fully valid Model:

```ts
{
  route: Post('123'),
  post: {
    id: '123',
    title: '',
    body: '',
    liked: true,
  },
}
```

The browser never receives the large `title`/`body`.

Whether those omitted baseline values are safe is addressed by static boundaries below.

# 6. The new handoff protocol

Current Foldkit hydration sends:

```html
<script
  type="application/json"
  data-foldkit-flags="root"
>
  ...
</script>
```

`foldkit-ssr` should introduce:

```html
<script
  type="application/json"
  data-foldkit-resume="root"
>
{
  "v": 1,
  "plan": "post-page",
  "state": { ... }
}
</script>
```

Effect Schema:

```ts
const ResumeEnvelope = Schema.Struct({
  v: Schema.Literal(1),
  plan: Schema.String,
  state: Schema.Unknown,
})
```

`state` is subsequently decoded using the `ResumePlan`'s own state Schema.

I would **not** repeat these in the JSON:

```text
runtimeId
buildId
field paths
Schema names
Surface names
Message names
```

unless needed.

The surrounding markup already identifies `runtimeId` and Foldkit's root already carries the `buildId`.

The `plan` ID distinguishes multiple SSR plans within one build.

### Payload safety

Implement a dedicated JSON-script encoder:

```ts
serializeJsonScript(value)
```

which escapes at least:

```text
<
>
&
U+2028
U+2029
```

so user data cannot terminate the `<script>` element.

Never emit executable JS:

```html
<script>
window.__STATE__ = ...
</script>
```

Always:

```html
<script type="application/json">
```

# 7. How we remove serialized Flags without changing Foldkit core

This is the useful trick.

Current Foldkit SSR does roughly:

```text
Flags
  ↓
init
  ↓
Model
  ↓
view
```

and then serializes Flags so `Runtime.hydrate` can reconstruct the Model.

Instead, `foldkit-ssr/server` can do:

```text
original Flags
      │
      ▼
original init
      │
      ▼
server Model
      │
      ├── ResumePlan.get(model)
      │        ↓
      │    resume payload
      │
      ▼
adapted no-Flags Foldkit app
      │
      ▼
upstream renderToString
```

The adapted config is essentially:

```ts
const serverModel = originalInit(...).model

const adapted = {
  ...config,

  // Remove Flags from the handoff.
  Flags: undefined,

  // Upstream Foldkit calls this, but it merely returns
  // the Model we have already constructed.
  init: () => ({
    model: serverModel,
  }),
}
```

Then delegate the actual VDOM serialization, hydration markers, build IDs, parser checks, head handling, etc. to upstream Foldkit.

Because Foldkit sees a no-Flags application, it has no reason to emit a Flags payload.

That lets us preserve Foldkit's server correctness instead of copying its internals.

### Important parity detail

Current Foldkit Schema-normalizes Flags before feeding them back into hydration/init. We should preserve that normalization in our wrapper before calling the original `init`.

# 8. Client startup skips the real `init`

The exact inverse works in the browser.

Instead of:

```text
deserialize Flags
      ↓
init
      ↓
Model
      ↓
view
```

do:

```text
Resume payload
      ↓
decode ResumePlan state
      ↓
App.initial
      ↓
ResumePlan.state.set(...)
      ↓
client Model
```

Then adapt the application passed to Foldkit:

```ts
const adapted = {
  ...config,
  Flags: undefined,

  init: () => ({
    model: resumedModel,
  }),
}
```

and finally:

```ts
Runtime.hydrate(adapted, {
  buildId,
  runtimeId,
})
```

So the existing Foldkit runtime still owns:

```text
Messages
update
Commands
Subscriptions
Mounts
Managed Resources
routing
DOM patching
```

We're only replacing its **initial state source**.

This is important architecturally:

> `foldkit-ssr` should not become a second Foldkit runtime.

---

# 9. The remaining problem: client `view`

At this point we've eliminated duplicate Flags.

But Foldkit's hydration still runs:

```ts
view(resumedModel, h)
```

The Model might now contain:

```ts
post.body === ''
```

while the DOM contains:

```html
<p>
  50 KB article...
</p>
```

Normal hydration would see a mismatch and rebuild it.

So we need a way to say:

> "This region is server-owned HTML. Do not reevaluate it in the browser."

This is the second major primitive.

# 10. `SSR.static`

Introduce:

```ts
SSR.static(
  'post-copy',
  ih => [
    ih.h1([], [model.post.title]),
    ih.p([], [model.post.body]),
  ],
)
```

The callback receives Foldkit's **inert builder**, not the application's normal `HtmlBuilder<Message>`.

That means server-static markup cannot accidentally declare Foldkit Message handlers at the type level.

Foldkit publicly exposes `inertHtml`; it is an `HtmlBuilder<never>`.

A complete page might look like:

```ts
const PostActionsView = Surface.rootView(
  PostActions,
  undefined,
  (model, h) =>
    h.div([], [
      h.button(
        [h.OnClick(Message.ToggledLike({ id: model.id }))],
        [model.liked ? 'Unlike' : 'Like'],
      ),
    ]),
)

const view = (model: Model, h: HtmlBuilder<Message>) =>
  Document.make(
    h.main([], [
      SSR.static('post-copy', ih => [
        ih.h1([], [model.post.title]),
        ih.p([], [model.post.body]),
      ]),

      PostActionsView(model, h),
    ]),
  )
```

Ownership is obvious:

```text
main
├── post-copy
│     SERVER STATIC
│     title
│     body
│
└── PostActions Surface
      CLIENT
      id
      liked
      ToggleLike
```

# 11. We can prototype `SSR.static` without changing Foldkit

This is the nicest implementation detail I found.

Foldkit already has exactly the primitive we need:

```ts
h.InnerHTML(...)
```

Foldkit's SSR implementation explicitly treats trusted `InnerHTML` as owning an opaque parser-produced subtree, and its hydration implementation compares equivalent parsed `InnerHTML` without reconstructing its children. Current Foldkit notes that equivalent trusted `InnerHTML` preserves existing child identities during hydration.

We can exploit that.

### Server rendering

`SSR.static` produces:

```html
<div data-foldkit-static="post-copy">
  <h1>Hello</h1>
  <p>Huge body...</p>
</div>
```

On the server the callback executes normally.

### Before client hydration

`Client.hydrate` scans:

```ts
root.querySelectorAll('[data-foldkit-static]')
```

and records:

```ts
Map {
  'post-copy' => element.innerHTML
}
```

### Client rendering

When the client executes:

```ts
SSR.static('post-copy', expensiveServerThunk)
```

the thunk is **not executed**.

Instead it returns conceptually:

```ts
ih.div([
  ih.Attribute('data-foldkit-static', 'post-copy'),
  ih.InnerHTML(snapshot),
])
```

where `snapshot` is the already-existing browser DOM.

So:

```text
server

model.post.body
      ↓
SSR.static thunk
      ↓
HTML
```

but:

```text
client

SSR.static
      ↓
lookup existing DOM
      ↓
trusted InnerHTML placeholder

NO model.post.body read
NO static child VDOM construction
```

This gives us a selective-hydration prototype **without modifying Foldkit core**.

That is a huge advantage.

# 12. Render context

`SSR.static` needs to know whether it's rendering for:

```text
normal SPA
server SSR
hydration/resumed client
```

Implement an internal synchronous render context:

```ts
type RenderContext =
  | { mode: 'server' }
  | {
      mode: 'resume'
      staticHtml: ReadonlyMap<string, string>
    }
```

and:

```ts
withRenderContext(context, () =>
  view(model, h),
)
```

Behavior:

```text
no SSR context
    SSR.static executes thunk
    normal SPA behavior

server context
    SSR.static executes thunk
    emits static boundary

resume context
    SSR.static DOES NOT execute thunk
    uses captured server DOM instead
```

The context only exists around the synchronous pure `view` call, so a simple stack is sufficient.

Do not keep request-global state active while asynchronous `init` work is happening.

# 13. Static boundary semantics

`SSR.static` should have very strict semantics:

> **The server owns this subtree for the lifetime of this document.**

That means the subtree may contain:

```text
text
images
links
semantic markup
native forms
server-produced HTML
code highlighting
large article bodies
product descriptions
tables
documentation
etc.
```

but may not contain Foldkit-managed interaction that must become live.

Because its builder is:

```ts
HtmlBuilder<never>
```

this already prevents normal Foldkit Message handlers.

If content needs to change because of a Message:

```text
it is not static
```

Move it into a Surface.

### Static content updates

A static boundary changes on:

```text
full navigation
reload
new SSR document
```

not on client Model updates.

That makes the rule very easy to understand.

# 14. The client side should be Surface-oriented

The recommended pattern becomes:

```ts
const ArticleActions = App.surface('ArticleActions', {
  model: ({ model }) => ({
    id: model.article.id,
    liked: model.article.liked,
  }),

  messages: [
    Message.ToggledLike,
  ],
})

const ArticleActionsRoot = Surface.rootView(
  ArticleActions,
  undefined,
  renderArticleActions,
)
```

and:

```ts
const view = (model, h) =>
  h.main([], [
    SSR.static('article-copy', ih => [
      ...
    ]),

    ArticleActionsRoot(model, h),
  ])
```

Now the distinction is structural:

```text
SSR.static
    server-owned view

Surface.rootView
    client-owned view
```

This is much cleaner than adding:

```text
server:
client:
resume:
remote:
```

fields to every Surface.

`Surface` already means:

```text
what this client-facing consumer observes
+
what it may cause
```

SSR should interpret that declaration rather than mutate its meaning.

# 15. Resume-state validation

`SSR.plan` should optionally accept the Surfaces that may be active:

```ts
const Resume = SSR.plan(App, {
  id: 'post-page',

  state: ClientState,

  surfaces: [
    Surface.at(Header),

    Surface.at(PostActions, model =>
      model.route._tag === 'post'
        ? { id: model.route.id }
        : undefined,
    ),
  ],
})
```

At server render time:

```text
active Surface
      ↓
Surface projection
      ↓
dependency paths
      ↓
compare against Resume state
```

If:

```text
PostActions reads:

post.id
post.liked
```

but Resume only contains:

```text
post.id
```

development should fail:

```text
[foldkit-ssr]

Surface "PostActions" reads client state that is not
available in the resume plan:

  post.liked

Add it to the Resume Projection,
satisfy it through a resume adapter,
or move the consumer into SSR.static().
```

That is the important correctness check.

# 16. The eventual "client closure"

Initially the state Projection should be explicit.

Later we can derive it.

Conceptually:

```text
client closure =
    active Surface Model dependencies
  + state required to determine active Surfaces
  + client-owned local state
  + Subscription activation state
  + Mount state
  + explicitly retained state
```

Everything else is eligible not to cross the wire.

But I would **not implement automatic closure derivation first**.

Start conservative.

Explicit:

```ts
SSR.plan({
  state: ClientState,
})
```

then validation.

After the semantics are proven, automate it.

---

# 17. Local state should default to retained

We should not aggressively remove arbitrary Model fields merely because a Surface does not currently read them.

Why?

Because:

```ts
update(model, message)
```

can read any Model field.

Unlike a Surface renderer, its dependencies are not statically declared.

Therefore the safe default should be:

> **Client-owned local state crosses the boundary unless explicitly classified otherwise.**

The biggest optimization opportunity isn't usually local UI state anyway.

It's:

```text
server data
article bodies
entity records
query results
CMS content
large loader payloads
```

which fits beautifully with `foldkit-remote`.

# 18. `foldkit-remote` integration

This is where the design becomes especially strong.

`foldkit-remote` already keeps server-owned facts in a normalized cache **inside the Foldkit Model**, and its requirement planner already derives what active Surfaces need.

That means SSR can eventually distinguish:

```text
Remote fact needed only by SSR.static
    ↓
do not hydrate it

Remote fact needed by active client Surface
    ↓
include exactly that fact

Remote fact needed later
    ↓
do not hydrate
    refetch when requirement activates
```

For example:

```text
Remote cache on server

Project:p1
├── id
├── title
├── 50 KB body
├── author
└── liked

Article page
├── SSR.static
│     title
│     body
│     author
│
└── LikeButton Surface
      id
      liked
```

wire payload:

```text
HTML
  title
  body
  author

Resume Remote cache
  Project:p1.id
  Project:p1.liked
```

not:

```text
HTML
+
the entire Project entity again
```

This is basically the ideal solution to the original double-data problem.

# 19. Resume adapters

To support Remote and future packages without teaching SSR about every state owner, define an extensible adapter interface.

Something like:

```ts
interface ResumePart<Model, Wire> {
  readonly id: string

  capture(
    model: Model,
    context: ResumeContext,
  ): Effect.Effect<Wire>

  restore(
    model: Model,
    value: Wire,
  ): Effect.Effect<Model>

  inspect(): ResumePartInspection
}
```

Built-in:

```ts
SSR.projection(ClientState)
```

Future:

```ts
Remote.resume(Data)
Sync.resume(...)
Durable.resume(...)
Mirror.resume(...)
```

Then:

```ts
const Resume = SSR.plan(App, {
  id: 'post-page',

  parts: [
    SSR.projection(ClientState),
    Remote.resume(Data),
  ],
})
```

Composition:

```text
baseline Model
      │
      ▼
Projection resume
      │
      ▼
Remote resume
      │
      ▼
complete client Model
```

No hidden store.

Every adapter merely constructs the same root Model.

---

# 20. Remote policy

The Remote adapter should probably support:

```ts
Remote.resume(Data, {
  policy: 'active-surfaces',
})
```

Meaning:

> include only cache facts required for the initial client-owned Surfaces.

Other possibilities later:

```text
'none'
    hydrate no remote cache

'active-surfaces'
    only initial client requirements

'all'
    entire current cache

custom(requirements => ...)
```

`active-surfaces` should be the preferred default for SSR.

```text
   │
   ▼

   ▼

   │
   ▼

   ▼
```


Consider:

# 23. One limitation of the initial `InnerHTML` implementation

The first implementation would snapshot:

```ts
element.innerHTML
```

for every static boundary.

So although static data is not duplicated **over the network**, it temporarily exists in browser memory as:

```text
DOM
+
snapshot string
```

That is acceptable for the experimental implementation because it proves the semantics without a Foldkit core patch.

But it should not be the final implementation.

# 24. Phase 4 — native opaque boundaries

Once the approach works, upstream one very small Foldkit primitive.

Something conceptually like:

```ts
h.Opaque(...)
```

or a reserved VNode property:

```ts
data.foldkitOpaque = true
```

Then the hydrator knows:

> adopt this element, do not descend into its children.

The client VNode becomes:

```text
selector
attributes
existing DOM reference
opaque = true
```

rather than:

```text
selector
InnerHTML snapshot string
```

That eliminates the memory duplication.

Importantly, this is a **small renderer primitive**, not a special SSR runtime.

It could be useful to Foldkit outside this package too.

# 25. Phase 5 — erase static view code from the client bundle

Even after eliminating duplicate data, this code still ships to the browser:

```ts
SSR.static('article', ih => [
  ih.h1([], [model.article.title]),
  ih.p([], [model.article.body]),
])
```

The browser doesn't execute it, but its JavaScript exists.

Add:

```text
foldkit-ssr/vite
```

which transforms client builds.

Server build:

```ts
SSR.static('article', () => {
  // full implementation
})
```

Client build:

```ts
SSR.staticRef('article')
```

Now the server-only rendering code itself disappears.

Tree-shaking can consequently eliminate imports used only by static thunks.

So:

```ts
import { renderMarkdown } from './markdown.server'
```

used only inside:

```ts
SSR.static(...)
```

doesn't need to enter the client graph.

That gives us:

```text
server data
  not shipped

server VDOM generation
  not executed client-side

server render code
  not shipped client-side
```

which begins looking much more like a genuine server/client ownership system.

# 26. Phase 6 — true Surface hydration boundaries

The current selective design still executes the top-level client view, although static thunks do almost no work.

A further optimization can make `Surface` itself the unit of hydration.

Server:

```html
<main>
  <div data-foldkit-static="article">
    ...
  </div>

  <div
    data-foldkit-surface="PostActions"
    data-foldkit-instance="p1"
  >
    <button>Like</button>
  </div>
</main>
```

The client could then instantiate only:

```text
PostActions
```

rather than execute the complete root view.

At that point:

```text
Surface
    =
smallest client-owned observation +
interaction +
rendering boundary
```

That requires a somewhat deeper Foldkit runtime seam because there must still be **one root Model and one root update function**.

Do not solve it by creating one independent Foldkit runtime per Surface.

That would destroy the architecture.

Instead, the upstream runtime would need to support:

```text
one Model/update runtime
        │
        ├── renderer: Surface A
        ├── renderer: Surface B
        └── renderer: Surface C
```

with projection-based invalidation.

I would treat this as a later Foldkit-core proposal after the simpler approach proves the semantics.

---

# 27. Phase 7 — binding-level resumability

This is optional and much more ambitious.

Right now client Surface renderers must execute once so Foldkit can reconstruct handlers such as:

```ts
h.OnInput(value =>
  Message.ChangedSearch({ value }),
)
```

That closure cannot simply be JSON serialized.

True "execute no view at startup" resumability would require build-assigned binding identities.

Conceptually:

```html
<input data-fk-binding="b17">
```

with the client bundle containing:

```ts
bindings['b17'] = value =>
  Message.ChangedSearch({ value })
```

Then the resume manifest could say:

```text
DOM b17
  input
  → binding b17
  → Message
```

and no initial Surface render would be necessary.

This would be Foldkit's equivalent of genuine resumability.

But it should be research work **after** selective SSR ships.

The likely benefit curve is:

```text
legacy hydration
      │
      ▼
selective state handoff       HUGE WIN
      │
      ▼
static boundary skipping      LARGE WIN
      │
      ▼
client code erasure           GOOD WIN
      │
      ▼
Surface-only hydration        GOOD WIN
      │
      ▼
binding resumability          diminishing / workload-specific
```

Do not begin at the bottom.

## 1. Add an “externally owned children” / opaque subtree primitive

Something like:

```ts
h.div(
  [
    h.UnmanagedChildren(),
  ],
  [],
)
```

Name is bikesheddable:

```text
UnmanagedChildren
OpaqueChildren
PreserveChildren
ExternalChildren
AdoptChildren
```

I think **`UnmanagedChildren`** communicates the semantics best:

> Foldkit owns this element, its attributes, listeners, lifecycle, etc., but **does not own or reconcile its child DOM**.

This actually fits Foldkit's existing hydration architecture unusually well. Hydration already walks the client VNode tree alongside the server DOM, creates a cloned VNode tree pointing at adopted DOM nodes, then performs an ordinary patch so modules can attach listeners/props/etc.

So for:

```html
<div id="article">
  <h1>Huge title</h1>
  <p>100 KB article...</p>
</div>
```

the client could render:

```ts
h.div(
  [
    h.Id('article'),
    h.UnmanagedChildren(),
  ],
  [],
)
```

and hydration would conceptually do:

```text
<div>
  ├── adopt host
  ├── attach Foldkit behavior to host
  │
  └── children
        ↓
      DON'T WALK
      DON'T VNODE-IFY
      DON'T PATCH
      DON'T DELETE
```

The implementation should also preserve those children on later patches while the marker remains present.

This isn't even inherently an SSR feature. It enables:

```text
server-rendered static content
third-party DOM widgets
syntax highlighters
maps/editors owning their interior DOM
legacy integrations
externally managed DOM
progressive enhancement
partial hydration
```

So it has a strong case for belonging upstream.

### Why I think this PR is especially defensible

Foldkit **basically already has this semantic internally through `InnerHTML`**.

Current hydration special-cases trusted `InnerHTML`, treating the subtree as parser-produced content rather than recursively reconciling its VNode children; equivalent `InnerHTML` can preserve the existing child nodes during hydration.

We're essentially generalizing:

```ts
h.InnerHTML(hugeString)
```

into:

```ts
h.UnmanagedChildren()
```

without requiring the content to exist as a second giant JavaScript string.

That is a clean conceptual extension.

For `foldkit-ssr`, it removes our ugly intermediate hack:

```text
server DOM
   ↓
element.innerHTML
   ↓
giant JS string
   ↓
h.InnerHTML(...)
```

and turns it into:

```text
server DOM
   ↓
adopt host
   ↓
leave children alone
```

Much better.

## 2. A second small upstream PR: render an already-created Model

Current `renderToString` owns:

```text
Flags
  ↓
init
  ↓
Model
  ↓
view
  ↓
serialize
```

Internally it literally computes the `initReturn`, takes `.model`, and runs the view over it.

I'd expose the lower-level operation.

Maybe:

```ts
Server.renderModelToString(
  {
    view,
  },
  {
    model,
    url,
    buildId,
  },
)
```

or perhaps a more Foldkit-ish name:

```ts
Server.renderPrepared(...)
```

Then normal `renderToString` becomes conceptually:

```ts
const { model } = init(flags, url)

return renderModelToString(
  { view },
  { model, url, buildId },
)
```

Why useful?

Because `foldkit-ssr` wants:

```text
run/init/load server data
          ↓
      server Model
          │
          ├── derive selective resume payload
          │
          └── render HTML
```

Right now we'd have to trick upstream SSR with:

```ts
const model = originalInit(...).model

const fakeConfig = {
  init: () => ({ model }),
  view,
}

Server.renderToString(fakeConfig, ...)
```

That works, but it's an adapter around an artificial `init`.

A lower-level API would make Foldkit's server renderer useful as a genuine interpreter:

```text
anything that can produce a Model
             │
             ▼
       Foldkit serializer
             │
             ▼
           HTML
```

That's also useful outside your project for databases, Effect HttpApi, SSG pipelines, tests, cached models, server actions, etc.

And since server rendering is explicitly still experimental, now is exactly the time to create this layering.

## 3. The bigger upstream improvement: separate DOM adoption from boot-state reconstruction

This is the architectural one I'd probably make an RFC before submitting code.

Right now:

```ts
Runtime.hydrate(app, {
  buildId,
})
```

has essentially one hydration protocol:

```text
read Flags from HTML
        ↓
Schema.decode
        ↓
init(flags)
        ↓
Model
        ↓
first view
        ↓
adopt DOM
```

The public `HydrateOptions` literally contains only `buildId`, and the documented behavior says hydration reconstructs the Model from the server-embedded Flags.

But those are actually two separate concerns:

```text
1. How do I obtain the initial client Model?

2. Should this first render adopt existing DOM?
```

I'd separate them.

Something conceptually like:

```ts
Runtime.adopt(
  app,
  {
    buildId,

    boot: Effect.succeed({
      model,
      commands,
    }),
  },
)
```

Then:

```ts
Runtime.hydrate(app, { buildId })
```

could simply remain the normal convenience API:

```text
deserialize Flags
    ↓
init
    ↓
Update.Return
    ↓
Runtime.adopt(...)
```

while `foldkit-ssr` could do:

```text
decode ResumeState
    ↓
restore Model
    ↓
resume startup Commands
    ↓
Runtime.adopt(...)
```

That would be a significant architectural improvement because Foldkit's existing concepts become:

```text
run
    Fresh DOM
    +
    fresh boot source

hydrate
    Adopt DOM
    +
    Flags/init boot source

adopt
    Adopt DOM
    +
    caller-defined boot source
```

### Important: use `Update.Return`, not just `Model`

This is something I would change from our earlier design.

Don't expose:

```ts
Runtime.hydrateModel(app, model)
```

because `init` isn't only a Model constructor.

It can also return Commands.

If we skip:

```ts
init()
```

and inject only:

```ts
model
```

we may silently lose boot-time Commands.

Instead the low-level primitive should start from something equivalent to:

```ts
Update.Return<Model, Message, Resources>
```

so:

```ts
{
  model: resumedModel,
  commands: resumeCommands,
}
```

is possible.

That keeps Foldkit's lifecycle semantics intact.

I actually think **this decomposition is valuable to Foldkit independently of resumability**. DOM adoption shouldn't fundamentally care whether the Model came from Flags, persisted storage, a server payload, a snapshot, devtools, a remote cache, or something else.

```ts
    [
      h.Class('article-body'),
      h.UnmanagedChildren(),
    ],
    [],
  )
```

Semantics:

```text
Foldkit owns:
  host element
  host attrs
  host props
  host classes
  host styles
  host events
  host Mount

Foldkit does not own:
  host.childNodes
```

Hydration:

```text
adopt host
skip recursive child matching
```

Patch:

```text
old unmanaged + new unmanaged
    → preserve children

old unmanaged + new managed
    → establish normal Foldkit ownership,
      replacing/reconciling children

old managed + new unmanaged
    → stop touching existing children
```

Fresh render:

```text
unmanaged + no existing children
    → simply produces an empty host
```

And then `foldkit-ssr` handles the server/client difference:

```ts
SSR.static('article', serverChildren)
```

compiles/interprets to roughly:

```ts
// server
h.div(
  [h.Attribute('data-fk-static', 'article')],
  serverChildren,
)

// resumed client
h.div(
  [
    h.Attribute('data-fk-static', 'article'),
    h.UnmanagedChildren(),
  ],
  [],
)
```

That removes almost all of the grossness from the prototype.

Then I'd follow it with **`Server.renderModelToString`** because that's another small, easily justified primitive.

Only after `foldkit-ssr` demonstrates the need would I propose the bigger **`Runtime.adopt`** abstraction.

So the upstream path becomes:

```text
PR 1
UnmanagedChildren
      ↓
PR 2
render existing Model
      ↓
build foldkit-ssr prototype
      ↓
collect benchmarks / real experience
      ↓
RFC
generic Runtime.adopt
      ↓
possibly later
deeper resumability primitives
```

That approach also gives the Foldkit maintainer something much easier to evaluate than “here is a giant resumability architecture.” Each upstream change stands on its own, while together they make your entire SSR design much cleaner.
