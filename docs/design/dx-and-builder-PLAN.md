# Plan: developer experience, view architecture, and the page builder

**Status:** phases 0 to 5 done, 2026-09-26, but for what each section's
dated note leaves: B9's regions as Slots (3d), words (3b), an
`Environment` (3a), an application's own commands (5a), hover as a Message
(5b), and rich text edited in place (5e). Phase 6 is still to decide.
Proposed, 2026-09-26. Addresses every item in
[dx-and-builder-FINDINGS.md](./dx-and-builder-FINDINGS.md): D1–D5, B1–B10,
X1–X2, and the underlying issues U1–U9. Item numbers below refer to that file.

Every API in this plan is a **proposal**. Names and signatures are what each
phase must make true, or deliberately replace, and are not yet code. Where a
design depends on something not yet checked, the phase opens with a spike and
says what the spike decides.

## The shape of the plan

Seven phases. Each rests on the ones before it:

```text
0 Workspace ──────────────► everything (faster loop, browser tests)
1 Styles ─────────────────► 2 (typed items compile to classes), 5f
2 Tests and Slot contracts ► 3, 4, 5 (every new view is checked)
3 View architecture ──────► 4 (the inspector is a part), 5
4 One control system ─────► 5 (commands, editing, patterns build on it)
5 Builder features
6 Decisions deferred on purpose (U9, X2)
```

A phase ships as small commits, as `AGENTS.md` asks. Every commit:

- updates the package README, the skill reference and `CHANGELOG.md` in the
  same change;
- carries tests that were shown to fail by mutation;
- passes `pnpm check` and a Jev review.

The example (`examples/cms`) moves onto each phase's API in the phase itself,
so every design is proven by an application before the next phase builds on it.

## Five rules the phases share

These come out of the findings, and each design below is checked against
them.

1. **One owner per fact, and presentation state is not a fact.** The Model owns
   what is replayed, stored, sent, or decides a Message. What matters only to
   pixels for a moment (hover, measured boxes, the caret) lives in a Behavior on
   the DOM (U1).
2. **Derive; do not list.** Nothing an application must keep in step by hand:
   not a stylesheet list, not a shortcut table beside a key handler, not
   aliases beside `paths` (D1, D2, B1). A declared list is fine where it is
   also the only way in, as a view's selection is (3c): then it cannot drift.
3. **One registry per concept.** One way to draw a control, one way to name a
   Block, one table of commands. A second package that needs a concept imports
   the first's registry (U4, X1, B1).
4. **Typed over strings.** What a package tells a stylist or a test travels as
   typed data on a Slot, not as a data attribute or an `aria-label` to spell
   (U8).
5. **Every claim has a test tier that can check it.** Logic in unit tests, view
   structure in inert tests, pixels and the caret in browser tests (U7).

**Goal.** Edit a package and see the change in the example and the tests at

Addresses D1 and the tooling half of U7.

### 0a. Spike: a source export condition (S)

Two packages (`foldkit-composition`, `foldkit-mixins-builder`) get:

```jsonc
"exports": {
  ".": {
    "foldkit-plus:source": "./src/index.ts",
    "types": "./dist/index.d.mts",
    "import": "./dist/index.mjs"
  }
}
```

with `customConditions: ["foldkit-plus:source"]` in a scratch tsconfig, and
`resolve.conditions` in the example's Vite config and in Vitest.

The spike answers three questions, and records the answers in this file:

1. Does `tsc -b` redirect an import resolved to a referenced composite
   project's source to that project's output declarations, as it does for
   `paths`, or does it compile the file into the importing project (TS6307)?
2. Does tsdown ignore the condition when building?
3. Does Vite serve a linked workspace package's source without pre-bundling
   it, and hot-reload it?

**Fallback if (1) fails.** The condition is used by Vite and Vitest only, and
tsconfig keeps resolving through `paths`, generated by a script (0c) rather
than kept by hand.

### 0b. Roll out (M)

  examples' `paths` blocks are deleted.
- The root `vitest.config.ts` loses its sixty aliases and gains

**Acceptance.**

- Changing a string in `packages/mixins-builder/src` changes the running

- `pnpm exec vitest run` in `packages/mixins-builder` runs against source (a
  deliberately broken source line fails it).
- The three configuration traps in `AGENTS.md` (package tests from the root,
  the stale Vite cache, `paths` coverage) are deleted or rewritten.

## Phase 1: styles

**Goal.** A style can never be missing. Package styles can always be
overridden. Conditional styles can carry rules. Addresses D2 and D3, and
prepares U8.

### 1a. The registry (M)

When a Style compiles (at module load, as now), it records each class it
produces:

```ts
// foldkit-mixins, internal
interface Registered {
  readonly className: string
  readonly css: string                 // the rules, each inside its @layer
  readonly global: ReadonlyArray<string> // keyframes and other global chunks
}
Style.registry: ReadonlyMap<string, Registered>  // read-only view
```

- Class names are already a hash of canonical CSS, so a class names one entry
  whoever compiled it, and the registry is identical on the server and in the
  browser. Registering the same class twice is a no-op. Two different CSS texts
  under one name would be a hash collision, reported as
  `style:class-collision`.
- The registry is data. Nothing touches the DOM at import, which keeps
  [mixins-DESIGN.md](./mixins-DESIGN.md)'s real constraint while dropping its
  "no render-time collection".

### 1b. Injection on insert, in the browser (M)

- A Style's contribution adds one insert hook to each element it styles. The
  hook calls `ensure(classNames)`.
- `ensure` keeps a Set of injected classes and appends each missing entry's
  CSS to one `<style data-foldkit-styles>` element through
  `CSSStyleSheet.insertRule`. One element rather than `adoptedStyleSheets`,
  so a CSP nonce can be applied (`Style.injector({ nonce })`) and the SSR
  element can be the same one.
- The first `ensure` inserts the layer order statement (`@layer reset, tokens,
  …;`) from the application's declared `Layers`, so rules inserted later still
  cascade by layer, not by insertion order. An application that declares no
  layers gets the standard order.
- The hook runs synchronously within the patch, before paint, so nothing
  flashes unstyled.

**Spike first (S).** Measure the per-element cost of the hook on a
1,000-row list in the browser tier. If it shows, batch per patch: collect
classes during the patch and call `ensure` once from the runtime's post-patch
point instead of per element.

> **1a and 1b done, 2026-09-26,** with two changes from the text above.
>
> - **At render, not on insert.** A Slot's attributes are resolved during the
>   draw; that is where the classes are queued (`inject.ts`, called from
>   `SlotView.buildersFor`), and a microtask appends them after the patch and
>   before paint. No hook per element, and the check is one Set lookup per
>   class per draw.
> - **No marker.** The injector finds the classes a page's stylesheets carry by
>   scanning their text for compiled class names (`.style-<hash>`) when it
>   makes its element, so `Style.stylesheet`'s output is unchanged. A sheet
>   removed later is not noticed; removing the injected element makes it
>   count again.
>
> The browser test that a Style left out of the stylesheet still draws, held
> as `it.fails` in 0c, now passes.
>
> **1f done:** the example's `sheet.ts` holds only its foundations, and
> `lookStyles` is gone; the studio and the site render as before.

### 1c. Server extraction (M)

- `foldkit-ssr` walks the rendered tree's classes after `renderToString`,
  looks each up in the registry, and emits one `<style data-foldkit-styles
  data-classes="…">` in the head.
- In the browser, the injector adopts that element on start and seeds its Set
  from `data-classes`, so hydration inserts nothing twice.
- A test renders a page on the server and in jsdom, and asserts the same
  classes and CSS. This replaces the compile-twice test that stood in for
  server/client equality.

> **1c done, 2026-09-26,** without a marker attribute: `Style.usedIn(html)`
> returns the layer order and the CSS of each compiled class the markup uses,
> and `foldkit-ssr`'s new `head` option (on `page`, `generate` and `entry`)
> puts it before `</head>`. The browser's injector finds those classes by
> scanning the sheet, as it does any other. `foldkit-ssr` does not depend on
> `foldkit-mixins`.

### 1d. Conditional rules: already done

The findings said `Style.whenInput` refuses a piece with rules
(`style:conditional-rules-unsupported`). That was true of an earlier version:
the refusal was lifted when [behaviors-DESIGN.md](./behaviors-DESIGN.md) was
ported, and a conditional piece already compiles to its own class. The claim
came from `mixins-DESIGN.md`, which was stale on the point. Nothing to build.

### 1e. Fixed declarations out of inline style (S)

The rule, written into the mixins README: **a declaration whose value is fixed
when the Style is defined is a rule in the Style's layer. A value known only
per element is an inline custom property, read by a rule.**

| Site | Change |
| --- | --- |
| `Prose.style` | `max-inline-size: var(--fk-prose-measure, 65ch)` and `line-height: var(--fk-prose-leading, …)` become a rule; `measure` and `leading` options set the variables |
| grid areas (`styleValue.ts`) | the template becomes a rule per distinct template (it is known at definition) |
| `Style.stagger` | `--fk-index` stays inline; the delay formula becomes a rule |
| `Appearance` token axis without breakpoints | `Style.self`, like the responsive case |
| the Builder's frame | `--fk-frame-width` inline, the width and margin in the frame's rule |
| the Renderer's edit wrapper | `display: contents` becomes one global rule on `[data-composition-node]` in the edit mode's sheet |

The check is Phase 2b's helper: rendering a package's views and recipes fails
on any inline property that is not a custom property. `Style.vars` and
`Style.inline` stay public for applications, documented as the escape hatch
they are.

> **1e done, 2026-09-26,** for Prose (with a `leading` option), grid,
> `stagger` and the Builder's frame (a default rule in `components` reading
> `--fk-frame-width`). Two sites stay inline, on purpose:
>
> - **An appearance token without breakpoints.** It is an author's choice on
>   one node, which should beat a stylist's defaults; and inline, the resolver
>   refuses a Behavior owning the same property ("two owners"), a check a rule
>   would lose. Tried and reverted.
> - **The Renderer's `display: contents` edit wrapper.** It is structure, not a
>   look, and `foldkit-composition`'s renderer draws without Styles.
>
> The check that no other inline declaration is fixed is Phase 2b's.

### 1f. The static sheet becomes optional (S)

- `Style.stylesheet(...)` stays, for foundations and for preloading what the
  first paint needs.
- The example's `sheet.ts` shrinks to the foundations: layers, reset, tokens,
  theme and defaults. The list of scoped Styles and `lookStyles` go.
- A development warning (`style:unregistered-class`) fires once per class an
  element carries that the registry lacks: a hand-written class, or a typo.
  **Dropped:** with injection, a list can no longer be forgotten. A class the
  registry lacks can only come from a second copy of `foldkit-mixins`, and the
  package has no warning channel to report it through. Revisit if seen.

**Acceptance for the phase.** Phase 0c's missing-style test passes. The
example has no list of scoped Styles. Prose's measure is overridable by a later
layer, with a browser test.

**Documentation.** `mixins-DESIGN.md` gets a dated note that render-time
injection replaced "no render-time collection", with the reason, pointing
here.

## Phase 3: view architecture

**Goal.** Package views can be restructured, not only styled. They draw only
what changed. They read environment facts and words the same way everywhere.
Addresses U1, U2, U3, U5, U6, and B9 and B10 on the way.

### 3a. `Environment` (S)

> **Built with 5a,** its first reader (the command table's key names), rather
> than ahead of any reader.

In `foldkit-mixins`:

```ts
const Environment = Schema.Struct({
  platform: Schema.Literals(['mac', 'windows', 'linux', 'ios', 'android', 'other']),
  locale: Schema.String,
  reducedMotion: Schema.Boolean,
  pointer: Schema.Literals(['fine', 'coarse']),
})
Environment.read: Effect<Environment>               // navigator and matchMedia, at the edge
Environment.changes: Subscription<Environment>      // matchMedia listeners
Environment.default: Environment                    // for tests and the server
```

The application keeps one in its Model and passes it to package views as an
input field. A package view declares the fields it reads in its input type, so
a view that needs `platform` fails to compile without it. Tests pass
`{ ...Environment.default, platform: 'mac' }`.

### 3b. Words (S per package)

One convention for every package that draws text:

```ts
export interface BuilderWords {
  readonly addBlock: (label: string) => string          // "Add Hero"
  readonly addsInside: (label: string) => string         // "Adds it inside the Section"
  readonly emptyPage: string

}

// the view input: words?: Partial<BuilderWords>
```

`foldkit-crud`'s `ViewWords` and the CMS's state words to the same shape. A
test per package renders with every word replaced by a marker and asserts no
English literal is left in the view (a checked claim, not a hope).

### 3c. Views that redraw only when what they read changes (M)

**Decision.** A view boundary declares what it reads, and **is given only
that**. A selection that is also the view's input cannot drift from what the
view reads: a read outside it is a type error, because the view never had the
rest.

This is [reactivity-DESIGN.md](./reactivity-DESIGN.md)'s Phase 1, which
needs no change to core Foldkit and can start in this repository. Two other
designs were weighed:

- **A dependency list beside the code** (`memo: input => [input.document]`,
  with `draw` still given the whole input). This is rejected, because the list
  drifts: a later read the list omits is a screen that silently fails to
  update. It is the same failure as `sheet.ts` and the shortcut table.
- **Tracking reads with a Proxy.** Also rejected, as §2 of that design
  prefers. A read that bypasses the proxy (module state, a clock) is still a
  stale screen. It costs a proxy per render. And the dependencies are known
  only at runtime, not in the code.

**Two forms, by what a view is drawn from.**

- **An application view over its root Model** selects with a Projection that
  carries its dependency paths (`Projection.struct`, `Projection.pick`, a
  `FieldRef`):

  ```ts
  const Sidebar = Reactive.view(
    Projection.struct({ posts: App.fields.posts, filter: App.fields.filter }),
    (value, h) => …,   // value: { posts, filter }, and nothing else
  )
  ```

  A `Projection.fromReader`, whose dependencies are unknown, is refused at a
  boundary (`reactive:unknown-dependencies`), since it could never hit.
- **A package view over its input** (a Bundle's Model plus view inputs) selects
  keys, typed as a `Pick`:

  ```ts
  Parts.part('Layers', { reads: ['page', 'selected', 'layers', 'drag'] }, (input, slots, h) => …)
  // input: Pick<BuilderInput, 'page' | 'selected' | 'layers' | 'drag'>
  ```

**How a boundary decides** (schematic):

1. Read each declared path's value from the new input.
2. Compare them by identity with the values from the last draw. The Model is
   updated immutably with structural sharing, so identity is enough.
3. If all are identical, return the cached VNode through `createLazy`. The view
   does not run, no VNodes are allocated, and Snabbdom does not diff the
   subtree.
4. Otherwise, build the selection (read the Projection, or pick the keys), draw
   it, and cache it.

Compare the declared paths, not the selection's output: a Projection may build
a new object on every read (reactivity §7). `createLazy` already restores
dispatchers, mount ownership and Submodel mapping on a hit (reactivity §4), so
none of that is reimplemented.

**Per-item boundaries.** A per-item Slot draws each item through
`createKeyedLazy`, with the item's own selection:
`slots.row.lazy(item, { node, open, selected: isSelected }, drawRow)`. A value
the item derives from the whole (whether *this* row is selected) is passed as
a plain boolean, so only the rows whose boolean changed miss.

**Renderer nodes.** `Renderer.render` draws each node as a keyed boundary on:

- the node's object, which `apply` shares when unchanged (§25 measured it);
- its marks as booleans (`selected`, `drop` zone, `editing`);
- its read data, when it is a Query Block.

Children come from their own boundaries. Editing one Heading then redraws one
node and its ancestors' shells, not the page.

**Attached Mixins.** A Style or Behavior contribution that reads the input
(`Style.whenInput`, a Behavior's `attributes`) runs inside the boundary. So
its reads must be inside the selection too. `Style.whenInput` and
`Behavior.slot` take their predicate over the part's selected input, not the
whole, which types it. Attaching a Mixin makes a new SlotView, so a cache is
never shared between differently styled views.

**A development check, not a mechanism.** In development, a boundary samples
its hits: it re-runs the view and compares the VNode with the cached one, and
warns (`reactive:stale-hit`) when they differ. That can only happen through a
read outside the selection, such as a closure over module state. The check
costs nothing in production.

**What the root still does.** The root view runs on every Model change, and
most of its boundaries hit. Skipping the root entirely needs core Foldkit's
persistent render region (reactivity §26), upstream. Pursue it only if the
measurement below shows the root pass still matters.

**Measure** before and after, in the browser tier: the 1,000-node page, a
keystroke in the inspector, a hover, a selection change. Record the numbers in
`pagebuilder-DESIGN.md` §25, and in `reactivity-DESIGN.md` as its Phase 1
result.

> **Renderer nodes done, 2026-09-26.** `Renderer.render` memoizes each node
> on `[renderer, h, mode, id, node, shown, data, mark, drop, ...children]`,
> with the structure still walked every render so a node reached twice is
> still caught. Two things found building it:
>
> - Foldkit's lazy slot needs a runtime frame and throws without one, and
>   Foldkit exposes no way to ask. The Renderer tries the slot and draws that
>   render uncached if it throws. **Upstream request:** a public `inRender()`.
> - A reused drawing must keep one place, so every node is keyed by its id;
>   without keys, a move patched one node's drawing into its neighbour's.
>
> A runtime test counts view calls; the Builder's parts and per-row
> boundaries come with 3d.
>
> **Per-item boundaries done with 3d, 2026-09-26,** as `slots.row.lazy(item,
> drawRow, args)`: one change from the design above. An item's key also holds
> what the Mixins gave the Slots it used for it, compared by value. So a
> Behavior's per-item attributes (a roving tab stop worked out from the whole
> tree) need no declared key to stay fresh. An item drawing that holds another
> is not cached. The development check is not built. Measured in
> `pagebuilder-DESIGN.md` §25 and in `reactivity-DESIGN.md`: hover, selection
> and a keystroke each went from about 50 ms to the next frame.

### 3d. Parts and an assembly (L)

**Design.** A package view is a set of parts over one Slots record and one
input, plus a default assembly.

```ts
// foldkit-mixins
const Parts = SlotView.parts(BuilderSlots)<BuilderInput, Message>()

// Each part declares what it reads, and is given only that (3c).
export const Palette = Parts.part('Palette', { reads: ['page', 'selected'] }, (input, slots, h) => …)
export const Layers = Parts.part('Layers', { reads: ['page', 'selected', 'layers', 'drag'] }, …)
// … Inspector, Canvas, Toolbar, Crumbs, History, Viewports, Alert, Live

// the default: what BuilderView.define returns today
export const assemble = (builder, layout = defaultLayout) =>
  Parts.assemble(layout(parts(builder)))

// an application's own
const Editor = BuilderView.assemble(PageBuilder, p => [
  p.Toolbar({ before: [PageTitleField] }),
  h.div(regions.start, [p.Palette(), p.Layers()]),
  h.div(regions.stage, [p.Alert(), p.Canvas()]),
  AssetsPanel,
  p.Inspector(),
])
```

- A part is a function of its selection of the assembly's input (3c), the
  Slot builders and `h`, and is a boundary: it redraws only when what it
  reads changes. It is not a separate SlotView, so Styles and Behaviors attach **once, to the
  assembly**, and reach every part through the shared Slots. Styling code
  written today keeps working.
- A part's Behaviors (the tree's keyboard, the canvas's pointer) are declared
  with the part, and the assembly attaches the parts it uses. A layout without
  the Layers part attaches no tree Behavior.
- An application's own element in a layout (the page title, an assets panel)
  is ordinary Foldkit, drawn with the assembly's `h`.
- `defaultLayout` draws B9's regions (`start`, `toolbar`, `stage`, `end`) as
  Slots, so the default markup gets B9's regions.
- The same pattern then applies to the CMS editor screen and `ListView`.

**Spike first (S).** Build the Palette and Layers parts and an assembly of
them, with the tree Behavior declared by its part. The spike decides whether
Behaviors can be declared per part and attached by the assembly with the
current `Behavior.attach`, or need a new `Parts.behavior`.

> **Done, 2026-09-26, but for regions and B10.** `SlotView.parts(Slots)<Input,
> Message>()` makes parts and an assembly. A part's Behaviors are declared
> with it over its selection, which answers the spike: the current
> `Behavior.attach` is not used for them, and no `Parts.behavior` was needed.
> A Mixin attached to the whole assembly that reads the input makes the
> parts it reaches redraw every time. It stays correct, just not cached.
> The Builder is `BuilderView.parts(builder)`, ten parts, with
> `BuilderView.assemble(render)` for an application's own layout and
> `define` as the default. The default markup is unchanged: B9's regions
> as Slots, and the CMS editor and `ListView`, are still to do.

**B10 lands here.** `Renderer.render`'s edit options take `Option`s
(`selected`, `drop`, and `editing` from Phase 5e). `RenderContext.on` returns
`Option<Message>`.

> **B10 done, 2026-09-26.** `selected`, `hovered`, `drop` and `editing` are
> `Option`s, and `on` returns one; the drawn Builder passes its Model's as they
> are.

## Phase 4: one control system

**Goal.** One way to draw a control, used by forms, the inspector and CRUD.
Blocks and looks carry their own words. The inspector becomes a form, and gets
every control forms have. Addresses U4 and X1.

### 4a. The control registry, shared (M)

`foldkit-mixins-form` already draws a control by its kind through
`Renderers<Message>`, and `FormView` already takes more (`renderers`). That
registry becomes the one:

- It moves to a subpath, `foldkit-mixins-form/controls`, with `defaultRenderers`
  and the `Renderers` type, unchanged in shape.
- `foldkit-crud`'s filter controls are drawn by it, and its own kind switch is
  deleted.
- An application registers its kinds once and passes the same `renderers` to
  every view that draws controls.

> **Done, 2026-09-26, smaller than written.** Checked against the code, two
> of the three bullets had no target: `foldkit-crud` draws no filter
> controls and has no kind switch (its `ListView` renderers draw read-only
> Displays, a different table), and the registry needs no subpath to be
> shared. The gap was the inspector: a Block prop asking for a control kind
> of the application's own threw "no renderer" there, since the settings
> forms took no renderers. `BuilderView.define(builder, { settings: {
> renderers } })` now takes the same function of the Message the form views

### 4b. Words for Blocks and looks, in composition (M)

```ts
Block.define('Hero', {

Appearance axes: values: ['plain', { value: 'lg', label: 'Large' }]

```

- `Composition.operationSchema` annotates each insert variant with its

  A test decodes the JSON Schema an agent receives and finds the description.
- `Composition.describe` prints a label where it differs from the name.
- `BuilderView.describe` is removed. The example moves its words onto its
  Blocks.

> **Done, 2026-09-26,** with one change: the words are a pipe step,
> `Block.words({ label, description, group })`, not a `define` option, so an
> application can word a Block another package defined (the rich-text `Text`)
> and there is one way to do it. `block.words` holds them resolved, the label

> `Catalog.describe` gains the words; `describe` prints a label that says more
> than the name; `operationSchema` puts each description on its insert.

### 4c. The inspector is a form (L)

**Design.** For each Block in the Catalog, the Builder derives, once and
lazily, a form over the node's settings:

```ts
// derived per Block by Builder.make; not written by the application
const Settings = Schema.Struct({
  props: block.Props,
  appearance: appearanceSchema(block),   // Literals per axis, optional; per breakpoint when responsive
  when: whenSchema(catalog.context),     // an optional eq per context key
  actions: actionsSchema(block, catalog.actions),
})
const SettingsForm = Form.make(`${block.name}Settings`, Settings, {
  inputs: inputHintsOf(block),           // the Block's Input hints, as form inputs
})
```

- **Ownership.** The Document owns the node's settings. The form's draft is a
  projection of them, plus text a field holds while it does not yet decode
  (a number typed as "1."). This is the "held draft" that `foldkit-form`
  already keeps.
- **Flow.** The Builder's Model holds `inspector: Option<{ id, form }>`.
  - Selecting a node fills the form from the node (`Form.fill`).
  - A form change whose field decodes applies one `setProp`,
    `setAppearance`, `setWhen` or `setAction`, grouped in history by node and
    field, so typing a word is one undo step.
  - A field that does not decode shows its error at the field and applies
    nothing.
  - When the node changes by another way (undo, the canvas, an agent), the
    form is refilled, except for a field holding undecodable text, which
    keeps it until blur.
- **Drawing.** The inspector part draws the form with `FormView` and the
  shared registry (4a), in the sections it has today (Content, Style,
  Visibility, Interactions), as the form's groups. A look of up to four
  values is a kind, `choice`, drawn as the segmented buttons.
- **What it unlocks.** Any control forms have (a color picker through
  `Input.bundle`, a date, an image picker, rich text) works in the inspector
  with no Builder change. A prop's Schema error shows at its field.
  `BuilderView.controls` becomes plain form input hints on the Block.
- **Removed.** `valueField`, `optionsOf`, `seedOf`, `contextField` and
  `controlFor` in `foldkit-mixins-builder`, about 400 lines.

> **Props done, 2026-09-26.** The spike answered both questions: one form
> per Block, made lazily, fits `Form.make`; and the Builder need not place it
> as a Bundle. It runs the form itself and holds its Model as JSON in
> `inspector`, since one fixed Model cannot name a per-Block form's type. Two
> findings changed the design:
>
> - A form checks a draft against its key's *type* side and cannot draw an
>   `Option`, so the settings form edits each prop on its *stored* side,
>   re-checked against the whole Schema. `toEncoded` drops a check made after
>   a transformation.
> - `h.submodel` needs a runtime frame, and `inertHtml` is the same builder as
>   every view's `h`, so a frameless drawing is found by asking a lazy slot,
>   which throws only for a missing frame. A catch around `h.submodel` itself
>   also caught its duplicate-slot error and drew a dead form.
>
> The inspector's Content is the form, drawn by `FormView`, styled through
> `settings: { field, form }`. `foldkit-mixins-form` gained `words.none` and
> shows a chosen value its choices lack as `? value`.
>
> **Action inputs done, 2026-09-26,** as forms of their own, one per Block,
> event and action, so `valueField`, the second control system, is gone.
> **Decided against:** looks and conditions as form groups. Each is a choice
> from a fixed list that the Builder's controls already draw through its
> Slots; a form would add a mapping to `setAppearance` and `setWhen` and
> draw nothing better.
>
> **Acceptance met.** A color picker given with `Input.bundle` is drawn in
> the inspector and edits its prop, with no Builder code (a runtime test); "abc"
> in a number and an undo while focused are tested. A control with
> Subscriptions or Resources cannot run in a form the Builder runs as
> functions, so `Builder.make` refuses one, naming its Block.

**Spike first (S).** A Form over one Block's `Settings`, filled from a node,
with one change mapped to `setProp`. It decides:

- whether one form per Block (derived lazily) or one form rebuilt on selection
  fits `foldkit-form`'s definition-time `Form.make`;
- how a responsive axis's per-breakpoint choices map to form fields.

**Acceptance for the phase.**

- The inspector draws a color picker for a prop that asks for one, with no
  Builder code.
- A number prop typed as "abc" shows a field error and changes nothing.
- An undo while a field is focused refills the field.
- The view tests from Phase 2 pass with the inspector's parts.

## Phase 5: the builder features

**Goal.** The page builder an author expects: commands, drag from the palette,
copy and paste, Patterns, text edited in place, a selection with a toolbar, a
true narrow preview, a narrow layout. Addresses B1–B8.

### 5a. One command table (M)

```ts
interface Command {
  readonly id: string
  readonly words: (w: BuilderWords) => string
  readonly keys: ReadonlyArray<{ key: string; mod?: boolean; shift?: boolean; alt?: boolean }>
  readonly run: (model: Model) => Option.Option<Message>
  /** Where it is offered: the toolbar, the node's actions, only the keyboard. */
  readonly placement: ReadonlyArray<'node' | 'toolbar' | 'keyboard'>
}
Builder.make(name, { …, commands?: (built: ReadonlyArray<Command>) => ReadonlyArray<Command> })
builder.commands        // the table
builder.keyCommand      // derived: the first command whose keys match and whose run is some
```

  are all drawn from `builder.commands`. `ACTIONS` and `SHORTCUTS` in

- Keys are drawn for `Environment.platform` (⌘ on a Mac).
- **While editing text** (5e), `keyCommand` offers only the editing commands:
  Escape to cancel, Enter to commit. This is one check in the derivation, not
  one per command.
- An application's commands (Publish, Preview) take keys and appear in the
  list like the Builder's. The example moves its Publish button onto one.

> **Done, 2026-09-26, but for three things.** `PageBuilder.commands` is the
> table (`{ id, label, keys, placement, run }`); `keyCommand` is derived from
> it; the node's actions, the toolbar (now `Toolbar`, its `toolbar` and
> `toolbarAction` Slots in place of `history`, `undo` and `redo`), their
> titles and the shortcut list are drawn from it; `Builder.make`'s
> `commands` changes it. `ACTIONS` and `SHORTCUTS` are gone. Not done:
> **labels are English** until words (3b); **the platform is a view input**

> Builder's fixed union cannot carry, so they wait for a design that maps
> one out. 5e's editing-only check is 5e's.

### 5b. Hover and the selection overlay (M)

- `Hovered`, `Unhovered` and `model.hovered` are removed. The canvas's and the

- The canvas part draws an `overlay` Slot, positioned from `--fk-selected-*`,

**Tests.** Unit: no Message on hover. Browser: the overlay follows the
selection through a scroll, and the hover box follows the pointer.

> **Overlay done, 2026-09-26; hover as a Message kept for now.** `Measure`

### 5c. Drag a new Block from the palette (M)

- `Drag` becomes `{ source: Existing(id) | New(block), over, at }`, and
  `DragStarted` takes a `source`.
- `at` for `New` comes from a dry-run `insert` with a throwaway id, as a move's

- A drop of `New` sends `InsertAsked({ block, at })`.
- The palette part declares `PointerDrag` over its items, with the item data

**Tests.** Unit for the landing rules. Browser for a drag from a tile to

> **Done, 2026-09-26,** without typed item data (2c): the tiles already carry

> attribute, within }` so a drag from the palette lands on the canvas's

### 5d. Clipboard and Patterns (M)

- **Commands** in the table: Copy, Cut, Paste, and Paste after/inside by the
  usual rule (`placeFor` by the tree root's Block).
- **The copy** is `Composition.takeTree(document, id)`. It is kept in the Model
  as `clipboard: Option<Tree>`, and a Command writes it to the system
  clipboard as JSON with a format tag (`application/x-foldkit-composition`,
  plus `text/plain`).
- **Paste** reads the system clipboard through a Command, decodes it with
  `Composition.Tree` and `onExcessProperty: 'error'`, mints ids, `rekey`s, and
  applies `insertTree`. `apply` checks every node against the Catalog. A
  refusal shows in the alert and inserts nothing. A test pastes a tree with
  an unknown Block, an invalid prop and an id that is already taken, and
  asserts each is refused whole.
- **Patterns.** `Catalog.make({ patterns: [{ name, words, tree }] })`, checked
  against the Catalog at definition, and offered as a palette group. Inserting
  one is a paste of its tree.
- **Agents.** `operationSchema` gains `usePattern: { pattern, at }`, the safe
  way to insert structure without accepting arbitrary trees. The pattern names
  are a literal union, so an unknown one is refused by the tool's own input
  schema.

> **Done, 2026-09-26, with three changes.** The system clipboard holds the
> copy as `text/plain` JSON tagged `{ format: 'foldkit-composition' }`, not a
> custom MIME type, which the async Clipboard API does not write; text read
> wins over the Model's `clipboard`, used only when the browser will not let
> it be read (`readText`, new in `foldkit-primitives/dom`). **`usePattern`
> is an Operation of its own**, `{ pattern, ids, at }` like `duplicate`, not
> a paste, so a replay makes the same nodes; in `operationSchema` its `ids`
> are a struct of exactly the pattern's node ids. **A pattern's tile is
> pressed, not dragged**: dragging one needs a third drag source, left until
> an author asks. The CMS example offers one pattern. Found on the way:
> `Measure` leaked a MutationObserver where ResizeObserver is missing; fixed.

### 5e. Text edited in place (L)

Three pieces, in this order.

**`EditableText`, in `foldkit-primitives/dom`.** A Behavior delegated from a
container (like `Targets`), over descendants carrying a field attribute:

- It reads `innerText` on input, never `innerHTML`, and drops line breaks for a
  single-line field.
- It reports nothing between `compositionstart` and `compositionend`, then the
  composed text once.
- Enter commits a single-line field, Shift+Enter breaks a multiline one, and
  Escape cancels and restores the initial text in the DOM, since the frozen
  view will not. Blur commits.
- It handles paste as text where `plaintext-only` is missing.
- It sends the owner's `onInput`, `onCommit` and `onCancel` Messages.

**The Renderer.** `RenderContext.field(key, text, { multiline? })`: in view
mode, the text. In edit mode, a span with `data-composition-field`. While
`options.editing` names this node and key, the span has
`contenteditable="plaintext-only"`, `role="textbox"`, an accessible name, and
**the text as it was when editing began (`editing.initial`)**. That freezing
is what keeps the virtual DOM from rewriting the element under the caret.

**The Builder.**

- `editing: Option<{ id, key, initial }>`.
- Double-click on a field, or the `edit-text` command (Enter on a selected node
  with one field), starts editing.
- Each input applies a `setProp` in one history group per editing session.
- Escape applies `initial` back into the group. `History` gains the rule that
  a group ending where it began records nothing.
- While editing, `Targets` does not `preventDefault` inside the field,
  `PointerDrag` does not start in it, and `keyCommand` offers only the editing
  commands. Each is a check on `model.editing`.
- A rich-text prop uses the Phase 7c-2 editor through the same `editing` state
  and history group.

**Tests.** Unit: the history rules, the stand-aside rules. Browser: the
caret survives a redraw during typing; IME composition reports once; Escape
restores; pasted HTML arrives as text; Backspace while editing deletes a
letter, not the block.

**Documentation.** `pagebuilder-DESIGN.md` §4 gets a dated note that the
canvas edits text in place under the freezing rule, pointing here.

> **Done, 2026-09-26, for plain text; rich text left.** `EditableText`
> (`foldkit-primitives`) also asks for editing on a double-click
> (`EditAsked`, since a canvas Renderer sends nothing) and focuses a field
> when it becomes editable. The Renderer's `field(key)` takes only text
> props (`TextKey`), names a field by node and prop as JSON, and keys the
> editable span apart so the browser's element is replaced when editing
> ends; `Renderer.fields` is how the Builder knows which props a node draws
> as fields. `History` gained `close` and `revert` rather than a rule about
> groups ending where they began, since a Document redone is never the same
> object. `PointerDrag` stands aside in editable text; `Targets` needed
> nothing, its click default being harmless there. **Not done:** a
> rich-text prop through the Phase 7c-2 editor. A browser test in the CMS
> example types into a heading through redraws, deletes a letter with
> Backspace, cancels with Escape and undoes the session; each piece it
> relies on was mutated and caught.

2. After 5a to 5d: commands, drag from the palette, copy and paste, and
   Patterns.
3. After 4c: the inspector with any control.
4. After 5e: text edited on the page.
5. After 5f and 5g: a true phone preview, and a builder usable on a tablet.

## Risks

- **Parts (3d) and the inspector-as-form (4c) are the two largest changes, and
  both break every Builder style and view test.** Each has a spike first, and
  each lands before any new consumer is written against today's shape. Both
  are allowed at 0.x.
- **Render-time injection (1b) moves a cost into the patch.** Measured in its
  spike, with batching as the prepared answer.
- **`contenteditable` (5e) is a browser-behavior surface.** The freezing rule
  and the browser tests are the mitigation. Where a case cannot be made
  reliable in one engine, that engine falls back to the inspector field with a
  note, rather than shipping a caret that jumps.
- **The source condition (0a) may not work for `tsc -b`.** The fallback keeps
  the rest of Phase 0's value.

## Out of scope

- Multiple selection. The Model has one `selected` throughout, and every
  design here keeps that open by taking one id where a list would later go.
- Real-time collaboration on a page. The Document's Operations are already
  replayable, which is the prerequisite; the transport is a separate plan.
- Composite Blocks (`pagebuilder-DESIGN.md` §21), which stay deferred.
