# UI SDK core: behavior inventory and Foldkit opportunities

Reviewed 2026-11-13 against UI SDK commit `d6996097b9f8dbe5fe98c3f04210b9daa969a06c` (`@ui-sdk/core` 0.1.0-beta.1) and this checkout at `2f03efe9a270b0fa41de74966f3a8467379653d1`. The UI SDK checkout is a sibling at `C:/Users/Patrick/ui-sdk-research`. This is a source and documentation comparison, not an exhaustive browser parity test. Beta APIs can change.

## Conclusions

UI SDK's principal idea is assembling headless components from small behaviors and slots. Its `definePrimitive` supplies a mutable per-instance store, APIs and slot lifecycles to framework adapters ([kernel](https://github.com/vercel-labs/ui/blob/d6996097b9f8dbe5fe98c3f04210b9daa969a06c/packages/core/src/foundation/kernel/primitive.ts)). Foldkit already offers typed slots and composition, but keeps durable interaction state in the parent Model and transitions in `update` ([mixins reference](../skills/foldkit-plus/references/mixins.md), [primitives reference](../skills/foldkit-plus/references/primitives.md)). Preserve that ownership. Copying the upstream controller or adding a second component store would undermine it.

The strongest opportunities are behavioral conformance and precise composition: keyboard and assistive technology parity, focus after removal, drag interactions, and popup lifecycle. Foldkit already ships roving focus, selection, typeahead, overlays, pointer drag, an accessibility pattern catalog and a large widget library. A matching name in either project does not prove equivalent behavior or a missing feature.

## Prioritized work

Before implementing any item, read the relevant UI SDK and Foldkit source and tests side by side. Trace the actual event handling, state transitions, lifecycle cleanup, accessibility behavior and edge cases, then use what they reveal to improve the existing Foldkit implementation. Check whether an upstream technique fits Foldkit's Model and `update` ownership, and verify any resulting behavior with checks appropriate to the change. The matrix is a starting point for that investigation, not a substitute for it.

1. **Shared accessibility conformance harness.** UI SDK's [pattern checks](https://github.com/vercel-labs/ui/blob/d6996097b9f8dbe5fe98c3f04210b9daa969a06c/packages/core/src/testing/check-pattern.ts) exercise roles, accessible names, relationships and keys for 15 APG patterns; its [direction checks](https://github.com/vercel-labs/ui/blob/d6996097b9f8dbe5fe98c3f04210b9daa969a06c/packages/core/src/testing/check-direction.ts) require a real focus movement and check mirrored arrows, and its [server checks](https://github.com/vercel-labs/ui/blob/d6996097b9f8dbe5fe98c3f04210b9daa969a06c/packages/core/src/testing/check-server.ts) expose browser-only reads. Foldkit's [pattern catalog](../packages/mixins-ui/src/patterns.ts) checks declared slot contracts, and individual browser tests exist. Add reusable behavioral scenarios against rendered widgets, with real Chromium for focus, layout and pointer claims. Start with listbox, tree, dialog and tabs; include RTL, disabled items, accessible names, nested overlays and SSR/hydration. Mutate each new assertion's behavior to prove it can fail. This is a test-infrastructure proposal, not evidence that existing widgets fail.
2. **Audit focus recovery.** UI SDK's [focus recovery](https://github.com/vercel-labs/ui/blob/d6996097b9f8dbe5fe98c3f04210b9daa969a06c/packages/core/src/foundation/focus/focus-recovery.ts) chooses a caller-supplied fallback for the innermost removed focused part and waits until removal settles. Foldkit's [FollowTabStop](../packages/primitives/src/dom/follow-tab-stop.ts) already follows the roving stop without taking focus from outside, while [TagsInput](../packages/mixins-ui/src/tagsInput.ts) separately focuses the input after removal. Test removal of the last item, collapsed branches, nested parts and an intentional focus move; consider extending the existing mechanism with an explicit fallback only if those cases require it. Check deferred focus of virtualized rows as well; Foldkit already supports orientation, RTL and virtual navigation in [RovingTabindex](../packages/primitives/src/interaction/roving-tabindex.ts).
3. **Audit drag and keyboard parity.** UI SDK provides keyboard and pointer reorder, tree subtree moves, cross-list transfer, drag previews and edge autoscroll ([reorder](https://github.com/vercel-labs/ui/blob/d6996097b9f8dbe5fe98c3f04210b9daa969a06c/packages/core/src/foundation/drag-and-drop/reorder.ts), [tree reorder](https://github.com/vercel-labs/ui/blob/d6996097b9f8dbe5fe98c3f04210b9daa969a06c/packages/core/src/foundation/drag-and-drop/tree-reorder.ts), [transfer](https://github.com/vercel-labs/ui/blob/d6996097b9f8dbe5fe98c3f04210b9daa969a06c/packages/core/src/foundation/drag-and-drop/transfer.ts)). Foldkit's [PointerDrag](../packages/primitives/src/interaction/pointer-drag.ts) has pointer/touch thresholds and drop zones and explicitly needs a separate keyboard path. Identify which applications need those operations; design keyboard actions, validation and announcements through Messages and `update`, using current tree/selection/LiveAnnounce rather than a parallel state owner. Test cancellation, disabled targets, moving descendants and scrolling; do not infer a missing feature solely from export names.
4. **Exercise overlay policy and lifecycle.** UI SDK [popup](https://github.com/vercel-labs/ui/blob/d6996097b9f8dbe5fe98c3f04210b9daa969a06c/packages/core/src/foundation/popups/popup.ts) incorporates opener modality, dismissal reasons, focus restoration, layers and positioning. Foldkit already combines dismissal, focus scope, inertness and scroll locking in [Overlay](../packages/primitives/src/interaction/overlay.ts), and uses platform behavior where appropriate. Run browser scenarios for nested modal/modeless layers, outside presses, pointer versus keyboard opening, removed triggers, focus restoration, and portaled theme inheritance. Make fixes at the existing seam, informed by [Anchor](../packages/mixins-ui/src/anchor.ts); avoid duplicating popup state.
5. **Targeted building blocks, only with a consumer.** Compare UI SDK's geometric navigation, lasso/cell ranges, canvas viewport and connections, and range manipulation against the actual grid, builder and canvas needs. Extract pure geometry or Model-owned Bundles only when a consumer demonstrates a gap. UI SDK's direct updates and `live` optimization warrant profiling, not bypassing Foldkit's renderer or Model by default.
6. **Make agent-facing discovery executable.** UI SDK publishes an organized behavior index and reusable checks. Foldkit already has `foldkit-plus docs`, the skill references and machine-readable slot patterns. Connect the existing catalog to short task-oriented examples and conformance results; keep the references synchronized and snippets typechecked. UI SDK's page-agent/history APIs overlap a different ownership boundary from Foldkit Surface and Agent: investigate capability and security semantics before proposing integration.

## Behavior families

The [upstream behavior index](https://github.com/vercel-labs/ui/blob/d6996097b9f8dbe5fe98c3f04210b9daa969a06c/apps/docs/content/docs/core/behaviors/index.mdx) is the authoritative name-by-name catalog, including subpath imports and guides; the list below inventories every helper in that index at the reviewed commit. The [core barrel](https://github.com/vercel-labs/ui/blob/d6996097b9f8dbe5fe98c3f04210b9daa969a06c/packages/core/src/index.ts) includes additional types and exports; component-specific entrypoints and value/testing subpaths are separate. Inclusion here describes upstream functionality, not an assertion of Foldkit parity.

- **Focus and keys:** single-tab-stop roving focus, grid and geometric movement, typeahead, recovery and keyboard input hints.
- **Text and matching:** input history, IME and locale handling, fuzzy scoring and match highlighting.
- **Selection:** item and rectangular selection, incremental cell updates and clipboard conversion.
- **Drag, direct manipulation and canvas:** pointer drag, list/tree reorder, transfers, auto-scroll, move/resize, gestures, ranges, pan/zoom and port connections. Many offer keyboard operations and announcements; verify each operation's contract in its source.
- **Lists and trees:** searchable listbox behavior, virtualized rendering calculations, bottom-following, scroll picking, inline editing, hierarchy and tri-state checking.
- **Motion and popups:** presence and findable panels, gesture math, popup slots/presets, anchored positioning, layering and dismissal.
- **Preferences and platform:** storage-backed preferences, color scheme, pointer kind, announcements, shortcuts and mobile viewport adjustment.
- **Kernel, observation and agents:** change/commit callbacks, undo, primitive slots, selective and direct updates, observation and page-oriented agent/history helpers. These are architectural comparisons, not drop-in Foldkit state management.

## Selected source observations

- [Reorder](https://github.com/vercel-labs/ui/blob/d6996097b9f8dbe5fe98c3f04210b9daa969a06c/packages/core/src/foundation/drag-and-drop/reorder.ts) supports horizontal, vertical and grid layouts, keyboard pickup/drop and cancellation, grouped moves, RTL and announcements. It keeps a draft during interaction and commits at the end; a callback may reject it.
- [Selection](https://github.com/vercel-labs/ui/blob/d6996097b9f8dbe5fe98c3f04210b9daa969a06c/packages/core/src/foundation/selection/selection-model.ts) uses item order and a range anchor, with selectable predicates, additive ranges and select-all. A rejected selection does not advance its anchor. This is a useful test case for Foldkit's existing Selection.
- The experimental [virtualizer](https://github.com/vercel-labs/ui/blob/d6996097b9f8dbe5fe98c3f04210b9daa969a06c/packages/core/src/foundation/lists/virtualizer.ts) retains keyed measurements and focused rows, searches the visible window and supports variable heights and find-in-page stand-ins. Compare those individual properties with Foldkit's virtual list before prioritizing changes.
- The experimental [stick-to-bottom](https://github.com/vercel-labs/ui/blob/d6996097b9f8dbe5fe98c3f04210b9daa969a06c/packages/core/src/foundation/lists/stick-to-bottom.ts) distinguishes following from a reader who scrolled away, tracks unseen content and preserves position on prepend. MessageScroller already documents the same three behaviors; compare edge cases with real scrolling tests.
- The experimental [resize](https://github.com/vercel-labs/ui/blob/d6996097b9f8dbe5fe98c3f04210b9daa969a06c/packages/core/src/foundation/direct-manipulation/resize.ts) supports keyboard, constraints, aspect ratio and multiple boxes, with a live draft and final commit. Canvas helpers do not make a complete accessible canvas automatically: authors must provide a keyboard path and textual connection descriptions.
- [Popup state](https://github.com/vercel-labs/ui/blob/d6996097b9f8dbe5fe98c3f04210b9daa969a06c/packages/core/src/foundation/popups/create-popup.ts) separates open from mounted so exit animations can complete. Test this lifecycle against Foldkit's existing presence and overlay combination.

## Boundaries and next steps

This review covers the behavior catalog and sampled implementation, not every branch of each helper or every component-specific export. The upstream [component directories](https://github.com/vercel-labs/ui/tree/d6996097b9f8dbe5fe98c3f04210b9daa969a06c/packages/core/src/components) include accordion, autocomplete, avatar, button, calendar, carousel, checkbox, collapsible, color picker, combobox, command, date input/picker, dialog, drawer, field, file input, hover card, input, label, listbox, menu/menubar/navigation menu, meter, number input, OTP, pagination, password input, popover, progress, radio, rating, resizable, scroll area, segmented control, select, separator, slider, switch, tabs, timeline, toast, toggle, token input, toolbar, tooltip, tree, trigger menu and waterfall. Their implementations compose the lower-level helpers; a component-by-component browser audit is a separate follow-up. Number, date, color, image and testing subpaths have further APIs outside the behavior index.

Suggested first milestone: select four existing widgets, run a shared keyboard/ARIA/RTL suite in Chromium, record failing scenarios as issues, and implement only demonstrated gaps. Then independently scope focus fallback and a real keyboard reorder consumer. Any published API change also needs the repository's Jev review and matching skill documentation.
