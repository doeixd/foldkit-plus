# UI SDK comparison: evidence ledger

Part of [#558](https://github.com/doeixd/foldkit-plus/issues/558). Baseline: Foldkit `3c601ebfb74f2497def7b5fe413e5a22fa816b2e`, UI SDK `d6996097b9f8dbe5fe98c3f04210b9daa969a06c`. This ledger is incomplete: each row of the [review matrix](https://github.com/doeixd/foldkit-plus/blob/ui-sdk-core-review/docs/ui-sdk-core-review.md#comparison-matrix) still needs an entry or an explicit disposition. Evidence below is source review, not a browser parity verdict.

## Windowed lists

**Disposition: justified deferral.** The windowing math overlaps. `keep` (render a row that has scrolled away) and find-in-page stand-ins stay on the UI SDK side until a Foldkit consumer fails without them. No API change.

Compared at UI SDK `d6996097` (`createVirtualizer`, experimental) and this tree:

- **What is drawn.** `createVirtualizer` lays rows out absolutely inside a scroller. `items()` is the overscan window plus whatever `keep()` names, so a focused row can stay mounted after it leaves the viewport. [WindowList](../packages/mixins-ui/src/windowList.ts) draws `[start, end)` in document flow between two spacers (`windowOf` over [visibleRange](../packages/primitives/src/state/virtual.ts)). Its `keep` drops measured heights for keys that left the list. [Virtual](../packages/primitives/src/state/virtual.ts) is the same range as a Bundle: the application renders `windowFor` and prunes heights with `Prune`. [VirtualGrid](../packages/data-grid/src/virtual.ts) windows rows and center columns at a fixed row height; pinned columns are the columns that stay mounted. [VirtualList](../packages/mixins-ui/src/virtualList.ts) is slots around `@foldkit/ui`'s own scrolling list (that package's source is not in this worktree). The adapter adds no extra rows.
- **Measurements.** Both sides key a measured size and estimate the rest. The virtualizer's `estimate` is per index, and a size measured above the scroll offset is added to `scrollTop` because those rows are out of flow. WindowList uses one `estimatedHeight` (`unmeasured: 'mean'` replaces it with the mean of measured rows) and in-flow spacers, so a drawn row's resize is the browser's. Its browser tests cover the document's full height, a bounded row count, content above the list, positions after measurement, and a deep link whose opened row stays put with `overflow-anchor` `auto` and `none` ([windowList.browser.test.ts](../packages/mixins-ui/test/windowList.browser.test.ts)). The virtualizer keeps every measured size until `reset()`. `Virtual.Prune` and `WindowList.keep` drop keys the list no longer has.
- **Bringing a row into view.** `scrollToIndex` aligns `auto` / `start` / `center` / `end` on the scroller. `VirtualGrid.reveal` returns the smallest scroll that shows a cell; the grid applies it. WindowList's `from` and `pageOf` open a no-script page at a row. domains-plus scrolls the document from the keys the page handles ([resultsList.ts](../examples/foldkit/domains-plus/src/client/resultsList.ts)), which is the #406 path, rather than holding a row mounted off screen.
- **Find in page.** With `connect({ findable })` the virtualizer loads [findable-rows](https://github.com/vercel-labs/ui/blob/d6996097b9f8dbe5fe98c3f04210b9daa969a06c/packages/core/src/foundation/lists/findable-rows.ts): one `hidden="until-found"` stand-in per row, in groups of 100, and `beforematch` scrolls that row to center. WindowList's spacers are `aria-hidden` and empty. The consumers (the widgets demo, domains-plus results) are search or browse pages whose text is the query, and no test shows find missing a row someone needed. A stand-in per row is the DOM the window exists to avoid.
- **Also on one side only.** The virtualizer is horizontal, reports `onEnd` once per `count` inside `endThreshold` rows, and owns its scroller in the instance. `Virtual.isAtEnd` / `distanceToEnd` answer the same "near the end" question and leave the load to the parent. `stickyHeader` and `masonry` are Foldkit layout helpers beside the bundle; masonry places every item, so it is not a window.

A virtualized roving widget should scroll the focused index into the window, as `VirtualGrid.reveal` does, before rendering it outside the window. The other helpers in the Lists index belong to other rows: `createListbox` with typeahead, `createStickToBottom` below, `createInlineEdit` with in-place editing. `bindScrollPicker` (the centered option on scroll, drag, or Page Up/Down) has no entry yet.

## Following new messages

**Disposition: implemented gap.** The follow, the unseen count, and holding a prepended page in place already overlapped. Two edges did not, and both are fixed in `FollowEnd`. No second owner.

Compared at UI SDK `d6996097` (`createStickToBottom`, experimental) and [MessageScroller](../packages/mixins-ui/src/messageScroller.ts):

- **Follow and stop.** Both follow growth while at the end and stop once the reader has moved up past a threshold (24px there, `NEAR` of 16px here). The virtualizer instance also stores `atBottom` apart from `following`, ignores its own `scrollTop` (`ours`), and can start not following or `release()`. The scroller's Model is `following` and `unseen`; the browser holds the scroll. `ScrollToEnd` already scrolls smooth unless `motion`, `travel`, or reduced motion is still, and the jump test waits until that scroll reaches the end.
- **Intent before the scroll.** A wheel upward, or ArrowUp, PageUp, or Home, sets the virtualizer's `following` false before a frame. The scroller used to wait until `scrollTop` decreased, so growth in that gap called `toEnd()` and put the reader back at the end. `FollowEnd` now stops on those inputs when they arrive. A touch does not: the virtualizer's `touchmove` only clears `ours`, and the scroll position still decides. [Browser tests](../packages/mixins-ui/test/messageScroller.browser.test.ts) dispatch the wheel and ArrowUp, append in that turn, and read the same `scrollTop` with the new row below. ArrowDown still follows.
- **Viewport.** The virtualizer observes the scroller, so a shorter viewport while following runs `toEnd`. The scroller observed only the log, whose box does not change when the viewport does. It now observes the viewport too. The same browser file shrinks the frame and expects the end to stay in view.
- **Prepend and unseen.** `prepend()` saves the distance from the end for the next growth. The scroller holds the first element in view by its layout position, so the application does not call anything when it loads older rows, and the browser test checks that spot a frame later. Unseen there is a boolean. Here `Appended({ count })` adds a count, and only the application can tell a new row from an older one.

The three mutations (wheel listener, key listener, observing the viewport) are killed by those browser tests.

## Keyboard routing and event ownership

- Foldkit 0.170's `OnKeyDownPreventDefault` receives a key and modifier flags, suppresses native default when it returns a Message, and filters IME composition. Its callback does not expose the native event's `repeat`, `defaultPrevented`, target or propagation controls. `OnKeyDownFocus` adds a focus target but has the same raw-event limitations.
- A named route table can lower to one `OnKeyDownPreventDefault` owner and document that repeats are accepted and propagation continues. This can support exact key/modifier overlap checks and leave unhandled keys native, but it cannot claim repeat-specific handling or consumer-first cancellation through that callback. UI SDK's [part event handling](https://github.com/vercel-labs/ui/blob/d6996097b9f8dbe5fe98c3f04210b9daa969a06c/packages/core/src/foundation/kernel/part.ts) checks composition and `defaultPrevented`.
- Foldkit's `streamFromKeyBindings` exposes richer repeat and typing policies through a DOM listener, but a Mount listener is not automatically an event claim in the mixin resolver. A naive wrapper could bypass protected-event and single-owner checks, and a mount-time closure can hold stale input. Do not introduce a no-op event handler as a pretend ownership claim.
- **Implemented for #554:** `Behaviors.Keyboard.behavior` uses the attribute callback, not a Mount listener, so resolver and `ChildAttribute` ownership still apply. Exact chords compose under one owner and duplicates name both routes. Unit/type tests cover routing, inference and conflicts; Chromium covers IME, modifiers, repeat, native editing keys, cancellation and propagation. Its search-field consumer composes Escape-to-clear and ArrowDown-to-open-results. Richer consumer-first cancellation or repeat filtering remains outside this slice because Foldkit's callback does not expose those controls.

## Removal recovery

- [FollowTabStop](../packages/primitives/src/dom/follow-tab-stop.ts) answers a removal only by moving to the container's roving tab stop: it reads the item attribute, never the removed row's neighbourhood, and it belongs to a component that owns a `current` in the Model. [#553](https://github.com/doeixd/foldkit-plus/issues/553) asked for contextual fallback and nested ownership, which are different questions; changing `FollowTabStop` to answer them would have changed its meaning for every roving widget.
- **Implemented for #553:** [FocusRecovery](../packages/primitives/src/dom/focus-recovery.ts) is one lifecycle-scoped Mount that observes its container, with `part(h, { to? })` marking the rows and `FOCUS_RECOVERY_PART` / `FOCUS_RECOVERY_TO` naming what it reads. Fallback order is the id named by the nearest marked part or marked ancestor (root-bounded, and an id matching two elements names none), then the next sibling, then the previous sibling, then the nearest enclosing part that can take focus, then nothing. Nested roots share one refcounted registry with `Leaving`, so a root never claims a part inside another and one Mount's teardown does not drop the other's boundary. A part that moved rather than went takes focus back; focus the reader moved elsewhere and teardown leave it alone.
- The id is matched by walking `[id]` elements, not by a selector, so a CSS-special id works; a missing or disconnected target falls through to the next answer rather than throwing. The Mount sends no Message: which element has focus is a DOM fact, and the Model does not learn it.
- **Evidence:** [browser tests](../packages/primitives/test/focus-recovery.browser.test.ts) cover next and previous, the removed last part, a named fallback, an ambiguous id, a missing id, the enclosing part, nested roots, focus moved elsewhere, reordering, teardown and two independent roots on one document; [unit tests](../packages/primitives/test/focus-recovery.test.ts) pin the attribute names; ten mutations of the Mount are each killed. The [dismissible-list fixture](../examples/widgets/src/ui-sdk-dismissible-list.ts) is the first consumer: a filter field with a CSS-special id, a clear-all button, keyed rows, and one nested branch, with [three browser tests](../examples/widgets/test/ui-sdk-dismissible-list.browser.test.ts) for the next row, the field named by the last row, the branch, and the list emptied from the clear button.
- **Not in this slice:** nothing is announced to assistive technology because this Mount causes no state change of its own.

## Exiting retained content

- [Presence](../packages/primitives/src/motion/presence.ts) owns how long an exit lasts. `Hide` moves `shown` to `hiding` and schedules `Hidden` for that generation; `Show` bumps the generation, so a late `Hidden` leaves the phase `shown`. The view drops the part only once the phase is `hidden`. Reduced motion sends the same `Hidden` immediately. There is no `transitionend` timer.
- **Implemented for #555:** [Leaving](../packages/primitives/src/dom/leaving.ts) is a Mount on the container. `leaving(h)` writes `data-fk-leaving` while a presence phase is `hiding`. Focus moves, by the same fallback as `FocusRecovery`, before the part becomes `inert`. Clearing the marker restores the `inert` the part had and does not take focus back. [FocusScope](../packages/primitives/src/dom/focus-scope.ts) stops containing while its element is leaving, and on unmount restores the previous focus only when focus would otherwise be lost. [HideOutside](../packages/primitives/src/dom/layers.ts) releases its inert set while its element is leaving, and hides the outside again when the marker goes.
- **Evidence:** [browser tests](../packages/primitives/test/leaving.browser.test.ts) cover next and previous, a descendant, a CSS-special id, an ambiguous id, a missing id, a prior `inert` value, a still-leaving descendant, nested containers, focus already outside, a fallback `HideOutside` had made inert, teardown, and two widgets. [Unit tests](../packages/primitives/test/leaving.test.ts) pin the attribute. [Focus-scope](../packages/primitives/test/focus-scope.test.ts), [layers](../packages/primitives/test/layers.test.ts), and [presence](../packages/primitives/test/presence.test.ts) cover the contain/restore window, the outside set, and reduced motion. The [leaving fixture](../examples/widgets/src/ui-sdk-leaving.ts) places two `Presence` slices (a row exit and a popup) with one nested branch: [unit](../examples/widgets/test/ui-sdk-leaving.test.ts), [browser](../examples/widgets/test/ui-sdk-leaving.browser.test.ts), and [server markup](../examples/widgets/test/ui-sdk-leaving.ssr.test.ts) cover a delayed drop, Keep during the exit, a stale `Hidden`, reduced motion, a popup that hands focus to its trigger, a surface that takes focus during the exit, and two instances.
- **Not in this slice:** `Overlay.modal` does not attach `Leaving` on its own. A widget that exits marks the part and attaches the behavior. Nothing is announced to assistive technology.

## Assembled-widget inspection

- There is no second contract graph. [Assembly](../packages/mixins/src/assembly.ts) reads the slots, behaviors, styles, and pattern the caller still holds, matched to the view's mixins by identity. [#556](https://github.com/doeixd/foldkit-plus/issues/556) asked for a serializable description of that assembly.
- **Implemented for #556:** `Assembly.describe` lists public slots (hidden ones omitted), attachments in order, pattern obligations, `A11y.validate` diagnostics, known links, and contribution conflicts. A conflict names both contributors, the slot, and the event or attribute. Omit `input` and a Behavior's events and attributes stay `unknown`; pass it and `attributes` runs against `SlotView.inertBuilder`, copying claim names only. What a closure reads stays `unknown`. A Surface contract or an Action keeps its kind and name. `Assembly.textOf` is a pure rendering of that value. A nested control the render closure builds is a `parts` entry, because describe does not call the view.
- **Evidence:** [unit tests](../packages/mixins/test/assembly.test.ts) cover public slots, attachment order, unresolved claims, both conflict kinds, secrets left out, links reduced to kind and name, a view and a dynamic mixin left uncalled, a missing pattern slot, and a style ordered before its behavior when there is no view. The [search field](../examples/widgets/src/ui-sdk-search-field.ts) exposes `searchInspection` and `searchInspectionView`: the view draws `textOf` and does not walk the widget again. [Its tests](../examples/widgets/test/ui-sdk-assembly.test.ts) cover the recipe and keyboard part, a resolved keydown with the clear label's text left out, and a second click owner named in the same text the view draws.
- **Not in this slice:** classes, attribute values, and mount actions are not part of the description. A mixin nested inside the render function stays unknown unless it is passed as a part. Inspection reports a conflict; the resolver still throws it at resolution time.

## Authorized part binding

- There is no second action catalog. [Ui](../packages/agent/src/parts.ts) maps a part id and a label onto a capability `Agent.expose` already published, then `invoke` calls `messages.dispatchUnknown`. [#557](https://github.com/doeixd/foldkit-plus/issues/557) asked for that binding. [#533](https://github.com/doeixd/foldkit-plus/issues/533)'s `Write.can` hint is not in the tree, so availability stays the capability's own `available`.
- **Identity.** The part id is stable across a remount. An occurrence id names one mount; a stale one is `None` and does not select another row. Several renderings that share a label are `Ambiguous`, and that result carries ids, not field values. A part with no mount is off the page and still discoverable. `invoke` does not take an occurrence and does not care whether the control is mounted.
- **Before metadata.** Discovery lists only capabilities `messages.available` currently offers, so an unavailable one is absent rather than described as unauthorized. It does not call `authorize` and does not report a refusal reason. The projection encoded by `context` is the value boundary: named fields are copied with `Object.hasOwn`, and the Model is not read. `invoke` then runs the runtime pipeline, so a refused principal dispatches nothing.
- **Evidence:** [parts.test.ts](../packages/agent/test/parts.test.ts) covers ambiguous labels, remount, off-page discovery, an exposed `toggle` that is not a part, an unavailable save, and an authorization refusal that does not dispatch. [draft.test.ts](../packages/agent/test/draft.test.ts) and [draft.browser.test.ts](../packages/agent/test/draft.browser.test.ts) share the save outcome checks: refusal, correlated failure, overlapping requests, and a button click that reaches the same `RequestedSave` update. The headless run never builds the view.
- **Not in this slice:** discovery does not re-run `authorize`, because that hook judges a concrete input. An independent read-only review of identity, cross-principal leakage, and completion correlation approved `43eeb0bee` and found no leak or mis-binding. The server remains the authority for the same predicate. The issue stays open.

## Widget authoring

- [#551](https://github.com/doeixd/foldkit-plus/issues/551) asked for a search field and an editable/dismissible list on the current public APIs, with a shipped control, a recipe override, an attached behavior, parent placement, and two independent instances, and for a helper only after the remaining repetition was recorded. It also asked the docs to distinguish using a widget, customizing it, assembling one, and authoring a primitive.
- **No new API.** The search field already did the assembly: `Input.view`, `Recipes.Input.extend`, `Behaviors.Keyboard`, a clear-label `Behavior.attach`, and two `Bundle` placements whose parent view does not construct the child Message. The dismissible list is the edit-and-remove consumer from #553: one `update`, `SlotView.forMessages`, keyed rows, `FocusRecovery` attached. It is one instance. Autocomplete is the popup that commits a selection, so no third fixture was added. Nothing here is a store, a second reducer, or a placement layer. #190 stays the owner of a future Block placement.
- **What inference does not see.** `SlotView.forMessages<SearchMessage>()` names the universe because the render callback does not annotate `h`. `(model: SearchModel)` is how the view's input is inferred. `Behavior.forSlots(SearchSlots)<SearchModel, SearchMessage>` is required for the clear label: its attribute callback mentions neither type, and without the arguments `Behavior.attach` does not match the view (TS2769). The same pair is required on `Behaviors.Keyboard`: without it the route's model is `unknown` (TS18046). `Submodel.defineView<SearchModel, SearchMessage>(SearchView)` is required so `placed.view(model, h)` stays a two-argument call. `Submodel.defineView(SearchView)` typechecks and infers a view-input parameter, and both placements then fail with TS2554 (expected 3 arguments). `Bundle.make` takes the Schemas as values. A wrapper that only moved this pair would restate it at one new call.
- **Checks.** `examples/widgets/test/ui-sdk-search-field.test-d.ts` rejects an unknown slot, a behavior whose input is wider than the view, and a foreign Message, at `Behavior.attach`. The Scene and browser tests already cover two instances. `@foldkit/oxlint-plugin@0.15.4`'s recommended rules, run with oxlint 1.47 on the two fixture files (the published `recommended.json` still says `excludeFiles`, which that oxlint rejects, so the rule table was copied), reported one finding: `SearchInputRecipe({})`. The call is now `SearchInputRecipe()`. The parent view constructs no child Message.
- **Type cost.** A cold `tsc -b examples/widgets` (TypeScript 7.0.2) checked in 6.669s, 4,028,180 instantiations, 912,803K. That is the whole showcase, not one widget. Ten extra copies of the explicit pair (`Behavior.forSlots<SearchModel, SearchMessage>`, `SlotView.forMessages<SearchMessage>().define`, `Behavior.attach`) raised it to 4,373,158 instantiations and 7.426s: 344,978 instantiations, about 76ms each. #190's per-Block allowance is 25,000 instantiations. A forwarding helper would call the same generics, so it would not buy the difference back. The probe file was not kept.
- **Not in this slice:** no pipeable assembly helper. The issue stays open.

## Accessibility obligations

- There is no second role catalog. [A11y](../packages/mixins/src/a11y.ts) already compares a Slots contract to a pattern. [#552](https://github.com/doeixd/foldkit-plus/issues/552) asked that a widget also name who provides navigation, focus, activation, and checked state, and that a rendered test cover the state a slot only publishes.
- **Declarations.** Obligation names are that closed set. A present slot's `obligations` are unsatisfied until support names a provider: a Behavior's `supplies` (`A11y.suppliedBy`), `A11y.native` (the element), or `A11y.delegated` (the provider's name). An empty name is refused. Publishing an event or an attribute does not supply one. An absent optional slot is skipped; a hidden slot is diagnosed and is not also obligation-checked. `A11y.validate(pattern, slots)` does not read obligations, so the catalog's structural gate stays green. Pass a support list, including `[]`, or call `A11y.bound`. A literal list that misses an obligation is a type error. A list typed only as `ObligationSupport[]` is judged when the call runs. `Assembly.describe` passes each behavior's declaration, so replacing one revalidates.
- **What ships the declaration.** `RovingTabindex` supplies navigation on the container and focus on the item. `ListNavigation` supplies those, and activation only when `commit` is set. `Behaviors.ToggleState` supplies `checked` only when `as` is `'checked'`. `Behaviors.Keyboard` does not supply navigation. `Patterns.Listbox` requires navigation on `items` and focus on `item` (activation stays on the commit path, which is optional). `Patterns.Checkbox` requires checked and activation on `checkbox`.
- **Evidence.** [a11y.test.ts](../packages/mixins/test/a11y.test.ts) covers a published attribute, a behavior removed, a runtime list, a native input, a named delegate, an unnamed delegate, an unknown name, an absent optional slot, and a hidden slot. [assembly.test.ts](../packages/mixins/test/assembly.test.ts) covers replacing the focus provider. [patterns.test.ts](../packages/mixins-ui/test/patterns.test.ts) covers the listbox and checkbox patterns. [list-navigation.test.ts](../packages/primitives/test/list-navigation.test.ts) and [roving-tabindex.test.ts](../packages/primitives/test/roving-tabindex.test.ts) cover the primitive declarations. [list-obligation.browser.test.ts](../packages/primitives/test/list-obligation.browser.test.ts) covers arrows past a disabled option, focus, and Enter. [obligations.browser.test.ts](../packages/mixins/test/obligations.browser.test.ts) covers `aria-checked` from `ToggleState` and a native checkbox's `.checked`.
- **Not in this slice:** tree, dialog, tabs, RTL, and nested dialogs from the plan's rendered-scenario list. Metadata is not WCAG conformance. A wide support array does not catch the wrong slot until runtime. A cold `tsc -p packages/mixins` checked in 4.05s (2,568,441 instantiations). Eighty extra literal calls, four obligations each, checked in 4.33s / 2,581,159 through `validate` and 4.20s / 2,581,299 through `bound`, so the literal gate is inside the noise of that check. The issue stays open.
